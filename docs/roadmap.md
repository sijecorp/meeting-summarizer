- 합계: human ~6주 / CC ~4일 (M6.5·M7 제외). eng review에서 자동 업데이트(D2)와 설정 파일 가져오기(D3)를 빼 M6이 줄었다.
- 설계 문서의 처음 추정(human ~3-4주 / CC ~2-3일)보다 큰 이유가 있다. 스펙 검토에서 운영 규칙(복구, 장치 변경, 절전, 대기열, 트레이, 온보딩)이 대거 추가됐다.
- **M0가 끝나면 M1~M6 추정을 다시 한다.** 특히 S1(캡처)과 S3(빌드) 결과에 따라 M2·M3 작업량이 크게 바뀐다.

브랜치: M1~M3는 PR #1로 master에 합쳤다. M4부터는 검증을 통과한 단계마다 master에 바로 커밋·push한다(사용자 결정 2026-10-15). M0의 스파이크 코드는 버리는 브랜치에 두고 master에 합치지 않는다.

각 마일스톤은 "끝 조건"을 모두 만족해야 끝난다. 끝 조건은 요구사항 ID(`REC-01` 등)로 추적한다.

코드를 쓰기 전에 설계의 가정을 확인한다. 결과는 모두 `docs/spike-results.md`에 남기고, 바뀌는 결정은 설계 문서와 이 로드맵에 반영한다.

**끝 조건**
- S1~S5 각각 통과 또는 "실패 시" 경로가 결정됨.
- `whisper-rs` 버전이 고정됨. (M3에서 0.16.0으로 고정했다. Windows MSVC + Vulkan 빌드는 M6 배포 워크플로에서 확인했다(2026-10-16))
- CPU 폴백 기본 모델이 정해짐.
- 용어집을 Whisper에도 넣을지 결정됨.
- M1~M6 작업량을 다시 추정함.
- **진행 관문** (eng review D13): 파일럿 후보 녹음 담당자가 이번 주 정기 회의를 실제로 녹음·공유했다. 하지 않았다면 이유를 기록하고, M1 진행 여부를 프로젝트 오너가 다시 결정한다. 자동 중단이 아니라 결정 시점이다.

**M2 범위 메모**
- macOS 시스템 오디오는 cpal 루프백 대신 직접 만든 전역 tap으로 연다(아키텍처 4.3). S1의 헤드셋 문제를 피하려는 것이다.
- 처리 대기열은 M3다. M2는 녹음이 끝나면(중단된 녹음의 "처리 계속" 포함) 상태를 `recorded`로만 바꾼다.
- OS 알림은 M5다. M2는 `recording://warning`·`recording://stopped` 이벤트와 앱 안 배너로만 알린다(장치 변경, 권한, 무음, 최대 길이, 디스크 부족, 절전).

**끝 조건**
- 양쪽 OS에서 60분 녹음의 시작·중간·끝 여러 지점에서 잰 두 트랙의 시간 차이가 0.25초 이하다. 정렬 규칙은 트랙마다 ±100ms에 10초 동안의 드리프트를 더한 만큼 허용한다(0.1% 드리프트에서 최대 0.21초, `clock.rs` 테스트). 설계 문서 S1의 0.125초는 4시간 0.5초를 60분으로 비례 환산한 값인데, 정렬 오차는 녹음 길이에 따라 쌓이지 않으므로 쓰지 않는다. REC-03의 0.5초 안이다.
- 아키텍처 12.2의 녹음 관련 수동 점검(헤드셋, 덮개, 강제 종료)을 통과한다.

| `queue.rs` 워커 실행: 구간마다 spawn, 녹음 시작 시 kill, 비정상 종료 시 GPU 1회 재시도 → `gpu_failed` → CPU, 알림 | TRN-06, TRN-09 |
| 비정상 결과 검사, 환각 필터 + 단위 테스트 | TRN-07, TRN-08 |
| `queue.rs`: 대기열(워커 2개 동시 실행, 나머지는 FIFO 대기), 대기열 위치, 재개 | TRN-01 |
| 진행률(%)과 남은 시간, 대기열 위치를 헤더 칩, 홈, 처리 중 화면에 표시(`meeting://progress`). 실패한 회의는 홈과 처리 중 화면에서 "다시 시도" | TRN-01, APP-07 |
| 설정 전사 탭: 모델 선택, 파일 상태, 다운로드·취소·직접 가져오기(`tauri-plugin-dialog`), 다운로드 주소, GPU 실패 안내. `transcribe://gpu-failed`는 앱 경고 배너 | ONB-01, ONB-02, ONB-07, TRN-06 |
| 처리 중 화면에 전사본을 읽기 전용으로 표시(`get_transcript`). 요약(M4) 전까지 결과를 보는 곳 | TRN-01 |

**M3 범위 메모**
- 백엔드와 화면을 나눠 진행했다. 백엔드 쪽(위 표의 `model.rs`~`queue.rs`, IPC 명령·이벤트, `ipc.ts` 타입 래퍼)을 먼저 만들고, 화면 쪽(홈 설정 카드의 모델 항목, 설정 전사 탭, 진행률 표시, 전사본 표시)을 붙였다(아키텍처 10.1).
- 다운로드·가져오기는 저장된 모델과 주소로 돈다. 저장하지 않은 변경이 있으면 두 버튼을 막고 먼저 저장하라고 안내한다.
- 홈 설정 카드의 "모델 받기"는 전사 탭으로 가지 않고 바로 받는다(ONB-01). 받기 상태는 앱에 하나다(아키텍처 10.1).
- 헤더 칩의 대기 수에 `transcribed`를 세지 않는다(APP-07에 적음). M4에서 요약 대기열과 함께 다시 본다.
- 정한 것: `whisper-rs` 0.16.0(whisper.cpp 1.8.3), HTTP는 `reqwest` 0.13 + `native-tls`(아키텍처 2), 워커 인자는 회의 id 대신 경로(5.3), 샘플링은 `whisper-cli` 기본값과 같은 beam 5(5.2), 구간 길이 5~12분(5.2), `transcript.json` 형식(5.2), `meeting://progress` 형식(10.2).
- 용어집은 S2 결과가 나올 때까지 initial prompt에 넣지 않는다(아키텍처 5.2).
- 전사가 끝난 회의는 `transcribed`에서 멈춘다. 요약 단계는 M4다.
- GPU 실패 알림은 `transcribe://gpu-failed` 이벤트까지다. OS 알림은 M5다.
- 개발용 모델 `tiny`를 모델 표에 더했다(아키텍처 5.1). 874MB를 받지 않고 처리 흐름과 화면을 시험할 수 있다.
- 빌드에 `cmake`가 필요하다(macOS: `brew install cmake`).

**끝 조건**
- S2의 실제 회의 녹음으로 **전사 시간만** 재서 NFR-01 목표 안에 들어온다(Mac 10분, Windows Vulkan 25분, CPU 60분). 이건 중간 점검이다. 요약까지 포함한 NFR-01 전체 판정은 M5 끝 조건에서 한다.
- 처리 중 새 녹음을 시작하면 실행 중인 전사가 모두 1초 안에 멈춘다.

- M3처럼 백엔드와 화면을 나눠 진행한다. 백엔드(`summarize.rs`, 대기열의 요약 단계, `store.rs`의 요약 저장, IPC 명령, `ipc.ts` 타입 래퍼, 요약 eval)를 먼저 만들고, 화면(검토 화면 편집·저장·전송 안 함·복사·`.md` 저장·"미정" 강조, 반출 고지, "로컬로 요약" 토글, 요약 실패와 다시 실행, 처리 중 화면의 요약 진행률)을 붙인다.
- 정한 것:
  - 한 회의는 대기열의 같은 자리에서 전사 → 요약까지 간다(동시 처리 2개 그대로). `transcript.json`이 있으면 요약만 한다(아키텍처 8.4).
  - LLM 연결이 없으면 전사를 마친 회의는 실패가 아니라 `transcribed`에서 기다린다. 연결을 저장하면 요약 대기열에 들어간다. 헤더 칩은 대기열에 있는 `transcribed`만 대기로 센다(APP-07).
  - 녹음이 시작되면 로컬 요약은 멈추고 녹음 뒤 요약부터 다시 한다. 클라우드 요약은 녹음 중에도 끝까지 간다(SUM-09). 삭제와 종료는 둘 다 멈춘다.
  - 요약할 연결은 요약이 시작될 때 정해 `meta.json`의 `llm_connection`에 남는다. "로컬로 요약"은 클라우드로 대신 보내지 않는다(아키텍처 6.1).
  - OpenAI 추론 모델용 호환 재시도(`max_completion_tokens = max_tokens + 8,000`, `temperature` 없음), 로컬 추론 모델의 `<think>` 제거, 잘린 답(`finish_reason: "length"`)과 빈 답은 실패(6.1).
  - 로컬 연결과 loopback 주소는 HTTP 프록시를 거치지 않는다. "로컬로 요약"한 전사본이 사내 프록시로 나가지 않게 하려는 것이다(6.1).
  - 토큰 추정은 글자 하나에 한 토큰이다. 처음의 `글자 수 ÷ 2`는 한국어에서 낙관적이었다(사용자 결정 2026-10-15, 6.3).
  - 로컬 서버가 입력을 말없이 자르면(`usage.prompt_tokens`가 입력 글자 ÷ 4보다 작음) 서버 컨텍스트 설정을 안내하며 실패한다(사용자 결정 2026-10-15, 6.1).
  - 긴 회의는 재귀 축약이 줄지 않거나 컨텍스트가 너무 작으면 "컨텍스트 토큰 설정이 너무 작습니다"로 끝난다(6.3).
  - 30자 미만 전사본은 `meta.json`의 `no_speech`로 표시한다(6.5). 스키마 버전은 그대로 1이다.
  - `.md` 저장은 Rust가 저장 대화상자를 연다(REV-05, 아키텍처 10.2). 웹뷰 권한은 더하지 않았다.
  - 상태 변경 이벤트 `meeting://status`는 두지 않는다. `meeting://progress`의 `status`로 충분하다(10.2).
- REV-02의 글자 수(머리말 포함, 12,000자 검사)는 M5에서 `slack.rs`와 함께 정확히 센다. M4 검토 화면은 요약 본문의 글자 수를 보인다.
- 화면 쪽(아키텍처 10.1):
  - 검토 화면은 `review`에서만 편집하고 마지막 입력 800ms 뒤 자동 저장한다. 저장은 순서대로 하나씩 보내고, 화면을 떠날 때와 "전송 안 함"·".md로 저장" 전에 남은 입력을 먼저 저장한다. 별도 저장 버튼은 없다. 저장 상태는 회의별로 화면보다 오래 살아, 떠난 뒤 실패하면 앱 배너로 알리고 다시 열면 그 입력을 되돌려 다시 저장한다.
  - "미정" 강조는 편집란 아래 경고 상자에 "미정"이 든 줄을 나열하는 방식이다. textarea 안의 글자를 칠하지 않는다.
  - 요약 경로 안내와 "로컬로 요약" 토글은 녹음 화면과 처리 중 화면이 같은 컴포넌트(`RouteNotice`)를 쓴다. 요약이 시작되면(`locked`) 토글은 사라지고, 요약하는 동안은 "…(으)로 보내 요약하고 있습니다"를 보인다. 검토 화면은 `meta`의 `llm_connection`·`summarize_local`로 "전송됨"을 보인다. "요약 다시 실행"의 연결 선택지에도 보낼 곳을 적는다.
  - 처리 중 화면은 회의가 `review`가 되면 검토 화면으로 넘어간다. "요약 다시 실행"은 처리 중 화면에만 두고 홈 목록은 오류 한 줄만 보인다.
  - 설정의 "새 회의를 기본으로 로컬에서 요약"은 로컬 연결이 있을 때만 보이고, 없으면 `false`로 저장한다.
- 사람이 해야 하는 것: 아래 끝 조건의 실제 LLM 확인(클라우드, 로컬 Ollama), 그리고 M0 녹음으로 만든 실제 고정 전사본 3개와 `expected.json`(아키텍처 12.3). 지금은 합성 전사본 하나(`synthetic-weekly`)로 eval 경로만 확인했다.

**끝 조건**
- 실제 회의 전사본으로 클라우드 연결과 로컬 Ollama 연결 모두 요약이 나온다.
- 요약 eval(아키텍처 12.3)이 고정 전사본 3개 모두에서 통과한다. 담당자가 언급되지 않은 액션 아이템이 "미정"으로 표시된다.
- 아키텍처 6.4의 실패 상황이 각각 올바른 메시지를 보여준다.

**M5 범위 메모**
- 한 번에 백엔드와 화면을 함께 만들었다(아키텍처 7, 10.1, 10.2).
- 정한 것:
  - S5 대체 경로는 실행 중에 자동이다: `markdown` 블록이 400 `invalid_blocks`로 거부되면 mrkdwn `section` 블록으로 한 번만 다시 보낸다(아키텍처 7.1). 그래서 S5는 실제 Slack이 어느 경로를 타는지 확인만 한다.
  - 글자 수(REV-02)의 기준은 `slack.rs` 하나다. 검토 화면은 `slack_length`로 머리말까지 센 값을 보이고, 전송도 같은 함수로 12,000자를 검사한다. 꼬리말은 세지 않는다.
  - 머리말의 일시는 회의 시작의 현지 시각이다. Rust는 현지 시차를 안전하게 읽지 못해 웹뷰가 그 시각의 시차(분)를 넘긴다.
  - 자동 재시도는 없다(응답을 잃었으면 두 번 올라간다). "다시 보내기"는 녹음자의 클릭이다. 같은 회의의 전송은 한 번에 하나이고, 보내는 중에 다시 연 검토 화면도 그것을 안다(`get_meeting`의 `sending`, 끝나면 `slack://finished`).
  - 성공은 200에 본문 `ok`뿐이다. 리다이렉트는 따라가지 않는다(프록시·SSO 로그인 페이지의 200, Referer로 새는 URL). 3xx와 그 밖의 2xx는 "응답을 확인하지 못했습니다"이고, 연결 뒤의 오류는 "응답을 받지 못했습니다"다. 둘 다 채널을 확인하라고 한다.
  - 멘션(`<!here>`, `<@U…>`, `<#C…>`)은 `<` 뒤에 U+200B를 넣어 두 경로 모두에서 글자로 둔다. 글자 수도 넣은 뒤로 센다. 대체 경로의 링크는 `https`·`http`·`mailto` 주소만 바꾼다.
  - 웹훅 URL은 키체인에서 Rust만 읽고, 오류 문구에도 나오지 않는다(응답 본문은 Slack 오류 코드 모양일 때만 보인다). `https://`만 받는다(`localhost`·loopback IP만 `http://`).
  - 보내기 전에 제목·본문을 `save_summary`와 같은 경로로 저장한다. 보낸 것이 저장된 것이다.
  - 수정 수는 생성본 본문과 전송본의 줄 단위 LCS다. 붙어 있는 삭제·추가는 한 곳이고, 제목이 바뀌면 1을 더한다(아키텍처 7.2).
  - 기본 채널: 웹훅이 하나면 그것, 아니면 아직 있는 `last_channel`, 아니면 첫 번째. 선택은 웹훅이 둘 이상일 때만 보인다(NFR-04 클릭 3번 유지). `last_channel`은 전송만 쓰고 설정 화면 저장은 덮지 않는다(`gpu_failed`와 같은 방식).
  - 보낸 뒤 검토 화면은 홈으로 가지 않고 읽기 전용으로 남아 "#채널(으)로 전송함 · 시각 · 수정 N곳"을 보인다.
  - OS 알림은 Rust가 보낸다. 웹뷰에는 플러그인 초기화 스크립트가 쓰는 `notification:allow-is-permission-granted` 권한 하나만 줬다. JS 패키지는 쓰지 않는다. 메인 창이 보이고 앞에 있으면 알리지 않는다. 클릭은 Rust `on_action` → `app://open-meeting` → 그 회의의 지금 상태로 화면을 연다(아키텍처 10.1, 11).
  - 녹음 자동 종료도 OS 알림으로 보낸다(M2에서 미룬 것). GPU → CPU 전환은 앱 안 배너만이다(열 회의가 없다). 앱 안 배너는 둘 다 그대로다.
  - macOS는 알림마다 기다리는 스레드와 0.5초 타이머가 알림이 지워질 때까지 남는다. 플러그인에 지우는 API가 없어, 메인 창이 포커스를 얻으면 objc2-foundation으로 이 앱의 알림을 알림 센터에서 모두 지운다. 그러면 기다리던 스레드도 끝난다(아키텍처 11.1).
  - 트레이는 새 이미지 자산 없이 기본 아이콘에 지름 40%의 색 점을 그린다. 처리 중은 대기열에 있는 회의 수(실행 + 대기)다.
- 사람이 해야 하는 것:
  - 실제 Slack 테스트 채널로 보내 머리말·본문·꼬리말을 확인한다(아래 끝 조건). 이때 실제 Slack이 `markdown` 블록을 받는지, 대체 경로(section)로 가는지 기록한다(S5).
    - 본문에 `<!here>`, `<@U…>`(테스트 채널 멤버의 실제 ID), `[x](!here)`를 넣어 보내고 아무도 멘션되지 않는지 확인한다.
    - 지원하지 않는 블록을 Slack이 400 대신 200으로 받는지 확인한다(200이면 대체 경로가 타지 않고 블록만 조용히 빠질 수 있다).
  - 실제 1시간 회의로 NFR-01을 잰다.
  - Windows 실기기에서 토스트 클릭이 회의로 가는지, macOS 배포 번들에서 알림 클릭과 트레이 점이 보이는지 확인한다. macOS에서는 창을 앞으로 가져오면 알림 센터의 이 앱 알림이 지워지는지도 본다. 지금은 단위 테스트와 빌드까지다. 앱을 실행해 알림·트레이를 눈으로 확인하지 않았다.
  - OS 알림 설정의 앱 이름은 번들 이름(`productName` = `meeting-summarizer`)이다. M6에서 정했다(2026-10-16): 번들 이름은 `meeting-summarizer` 그대로 두고, OS가 보이는 앱 이름을 가리키는 안내 문구(일반 탭의 알림 안내, 시스템 오디오 테스트의 권한 안내)를 `'meeting-summarizer'`로 맞췄다. 헤더·트레이·알림 제목의 "회의 요약"은 그대로다.

- 테스트 채널에 실제로 보낸 메시지에서 머리말·본문·꼬리말이 의도대로 보인다.

Windows는 빌드만 확인했고 실제 PC에서 설치·실행은 아직이다.
- 사람이 해야 하는 것:
  - macOS 실기기: 시스템 오디오 녹음 권한이 없을 때와 있을 때 시스템 오디오 테스트가 실패·통과하는지, 테스트음이 거슬리지 않는지 본다. 출력 음량을 꺼도 통과하는지 기록한다(tap이 음량 전의 소리를 듣는다고 보고 실패 안내에서 음량을 뺐다). 블루투스 헤드셋처럼 지연이 큰 출력에서 1.2초 듣기로 충분한지와 -40 dBFS 기준이 맞는지는 `cargo test --lib on_this_machine -- --ignored --nocapture`(`audio/check.rs`, 실제 장치로 테스트음을 내고 들은 dBFS를 찍는다)로 확인한다. 마이크 권한을 아직 묻지 않은 상태에서 마이크 테스트를 누르면 팝업이 뜨고, 허용 뒤 레벨이 움직이는지 본다. 테스트 중에 ⌘R로 녹음을 시작하면 테스트가 멈추고 `system.wav`에 테스트음이 없는지 본다.
  - Windows 실기기: 같은 점검. Windows 코드(WASAPI 루프백으로 듣기, 고른 출력 장치로 재생)는 여기서 빌드하지 못해 확인하지 않았다.
  - 실제 Slack 테스트 채널로 테스트 메시지를 보내 문구와 녹음자 이름 줄을 본다.
  - Windows PC에 setup.exe를 설치해 앱이 뜨는지(`vulkan-1.dll`이 실행 파일 옆에 있는지), GPU 전사와 시스템 오디오 테스트가 되는지 확인한다. 빌드는 Actions에서 확인했다(2026-10-16).
  - 받은 `.dmg`를 다른 Mac에 설치하고("그래도 열기") 녹음이 0 버퍼가 아닌지, 업데이트 뒤 권한을 다시 물을 때 `docs/install.md`의 안내대로 풀리는지 본다(아키텍처 12.2).

**선행 외부 조건**: Open Question 1(Apple Developer 계정)은 해결되지 않았다. 사용자 결정(2026-10-16)으로 대체 경로를 계획으로 삼는다: macOS는 ad-hoc 서명만 한 내부 배포 빌드다(공증 없음). 계정이 생기면 워크플로의 주석 처리된 `APPLE_*` Secrets를 채우면 된다.

**끝 조건**
- 깨끗한 Mac과 Windows PC에서 설치 파일 실행부터 첫 Slack 전송까지 15분 이내, 터미널 명령 0개(NFR-03). macOS에서 처음 열 때의 "그래도 열기"는 시스템 설정의 버튼이라 터미널 명령이 아니다. M6.5 뒤에는 요약 모델까지 두 모델(약 3.4GB)을 받는 시간을 포함해 M6.5 7단계에서 잰다.
- 배포 빌드(ad-hoc 서명, Hardened Runtime)에서 녹음이 0 버퍼가 아니다.

## M6.5 로컬 요약 기본

계획: [docs/plans/2026-10-16-local-summary.md](plans/2026-10-16-local-summary.md) (승인 2026-10-16). 사용자 결정(2026-10-16): 클라우드 API 비용, 키 배포와 결제 승인, 회의 내용 반출 때문에 앱에 내장한 작은 LLM으로 요약하는 것을 기본으로 한다. 클라우드 연결은 선택으로 남긴다. 0단계 검증 관문은 두지 않았다(최종 관문 UC1).

| 1. 사이드카 빌드: llama.cpp `llama-server` 고정 커밋 정적 빌드(AVX2 기준, macOS Metal, Windows Vulkan), `externalBin`, 같은 빌드 작업에서 테스트, NOTICES | 아키텍처 11.3, 13 |

| 7. 실측 | NFR-01, NFR-03 |

**M6.5 진행 메모**
- 끝난 것 (2026-10-19): 1~4, 6단계와 8단계 문서. 요약 모델은 4단계 실측 뒤 Qwen3.5-4B에서 Qwen3-4B-Instruct-2507로 바꿨다(D7, 2.5GB, q8_0 KV 캐시로 1시간 회의 최대 메모리 약 5GB, 아키텍처 5.1·6.6). 프롬프트는 v4다(아키텍처 6.2).
- 미룬 것: 5단계 실행 중인 Ollama·LM Studio 찾기와 느린 PC 속도 안내(최종 관문 UC2, `docs/TODOS.md`).
- 남은 것: 7단계 실측. M1~M3 Mac과 Windows(내장 GPU, CPU)에서 1시간 회의 요약 시간·메모리, 8GB Mac, 첫 설치 다운로드 시간, 배터리 모드, AVX2 고정의 비용, Windows Vulkan에서 q8_0 KV 캐시와 flash attention(아키텍처 11.3), 동료 한 명이 도움 없이 설치부터 첫 전송까지. 숫자가 나오면 NFR-01·NFR-03을 고친다. M1이 5분을 넘으면 `-c`를 낮춰 다시 재고 품질 평가도 다시 돌린다. 반복 억제 값도 그때 정한다.
- 사람이 해야 하는 것: 7단계 실측, 그리고 1단계 확인 중 실기기가 필요한 것(회사 관리 Windows PC와 사내 백신에서 `llama-server.exe`가 격리되지 않는지, 받은 dmg를 설치하고 "그래도 열기" 뒤 첫 내장 요약과 업데이트 뒤 요약, 아키텍처 12.2).

**끝 조건**
- 새로 설치한 앱이 Slack 로그인 말고는 설정 없이 녹음 → 전사 → 이 PC에서 요약 → 검토 → Slack 전송까지 된다(2026-10-20 전에는 Slack 웹훅).
- 요약 모델을 받은 PC는 앱을 다시 설치해도 다시 받지 않는다.
- 내장 요약 중 녹음을 시작하면 요약이 멈추고 엔진이 꺼진다(SUM-09, SUM-12).
- 7단계 실측으로 NFR-01·NFR-03 숫자가 정해졌다.
