## 1. 전체 구조

```
┌──────────────────────── Tauri 앱 (단일 프로세스) ────────────────────────┐
│                                                                          │
│  React (WebView)                    Rust 백엔드                          │
│  ┌──────────────┐   invoke    ┌──────────────────────────────────────┐   │
│  │ 화면 6개      │ ─────────▶ │ commands.rs                          │   │
│  │ (상태로 전환) │ ◀───────── │                                      │   │
│  └──────────────┘   events    │  audio/ ──▶ meetings/{id}/*.wav      │   │
│                               │     │                                │   │
│                               │     ▼ (녹음 종료)                    │   │
│                               │  queue ──▶ transcribe/ ──▶ summarize/│   │
│                               │                         │            │   │
│                               │  slack.rs ◀── (검토 후 전송 버튼)    │   │
│                               │  store.rs (meta.json)  settings.rs   │   │
│                               └──────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────────────┘
        │ 모델 다운로드          │ LLM 요청              │ Slack 웹훅
        ▼                       ▼                       ▼
   Hugging Face          클라우드 API 또는          hooks.slack.com
   (또는 사내 미러)      로컬 Ollama/LM Studio
```

- 무거운 일(녹음, 전사, 요약, 전송)은 모두 Rust에서 한다. React는 화면만 그린다.
- React → Rust는 `invoke`(명령), Rust → React는 이벤트(진행률, 레벨, 상태 변경)로 통신한다.
- 데이터는 모두 녹음자 PC의 앱 데이터 폴더에 있다. DB와 서버는 없다.

## 4. 녹음

### 4.1 스레드 구조

```
캡처 스레드 (스트림 열기, 1초 폴링)
  cpal 콜백 (마이크)        ── 링 버퍼 ──┐
  cpal 콜백 (시스템 오디오) ── 링 버퍼 ──┴▶ 기록 스레드 (20ms마다) ──▶ mic.wav / system.wav
                                               └─▶ 레벨 이벤트 (40ms마다 React로: RMS + 스펙트럼)
```

- 오디오 콜백은 장치 샘플(인터리브 f32)을 트랙별 `rtrb` 링 버퍼(2초 분량)에 넣기만 한다. 콜백 안에서 할당, 락, 파일 I/O를 하지 않는다. 버퍼가 차면(기록 스레드가 멈춘 경우) 나머지를 버리고, 빈 구간은 4.2의 무음 채우기가 메운다.
- 스트림을 다시 열면 새 링 버퍼를 만들고, 받는 쪽을 채널로 기록 스레드에 넘긴다. 기록 스레드는 이전 버퍼에 남은 샘플을 먼저 쓴 뒤 바꾼다.
- 기록 스레드가 트랙마다 다음을 한다: 채널 다운믹스(모노) → 16kHz 리샘플 → 시간축 정렬 → 16-bit PCM으로 `hound`에 기록. 리샘플러의 시작 지연만큼 앞부분을 잘라 소리가 늦게 밀리지 않게 한다.
- **레벨 이벤트** (REC-09): 기록 루프가 20ms마다 돌므로 그 배수인 40ms마다 보낸다(초당 25번). 트랙마다 RMS와 스펙트럼을 담는다. 스펙트럼은 기록한 16kHz 모노 샘플(무음 채우기 포함)의 최근 1,024개(64ms)에 Hann 창을 씌워 실수 FFT(`realfft`, rubato가 이미 쓰는 버전)를 하고, 80Hz~8kHz를 로그 간격 24개 대역으로 나눠 대역마다 가장 큰 빈을 dBFS로 바꾼다. -80~-20dBFS를 0~100으로 맞춘다. FFT 계획과 버퍼는 녹음을 시작할 때 한 번 만들어 두고 다시 쓴다. 무음으로 채운 구간(권한을 기다리는 동안 포함)은 모든 대역이 0이다. 15분 무음 판정(REC-05)은 40ms 레벨 창이 아니라 1초 평균으로 한다. 짧은 딸깍 소리 하나로 15분을 처음부터 다시 세지 않게 하려는 것이다.
- `hound::WavWriter::flush()`를 5초마다 불러 헤더의 길이 필드를 갱신하고, 같은 파일의 두 번째 핸들로 `sync_data()`를 불러 디스크에 내린다(REC-02, NFR-05). 그래서 전원 차단에도 손실은 최대 5초다. sync 실패는 쓰기 오류와 같이 처리한다(4.6).
- 녹음 종료는 언제나 기록 스레드가 마무리한다. 두 WAV를 finalize하고, `meta.json`에 길이·`gaps`와 `recorded`를 쓰고, `recording://stopped`를 보낸다. 사용자 종료, 4시간, 절전, 디스크 부족, 쓰기 오류가 모두 같은 길이다.
- 절전 방지(`keepawake`, REC-06)는 기록 스레드가 녹음 동안 쥐고 있다. Windows `SetThreadExecutionState`가 스레드 단위라서다.

### 4.2 시간축 정렬 (REC-03)

- 기준 시계는 `clock.rs`의 **절전을 세지 않는 단조 시계**다. macOS는 `CLOCK_UPTIME_RAW`(= `mach_absolute_time`), Windows는 `QueryUnbiasedInterruptTime`을 쓴다. 둘 다 OS가 "절전·최대 절전 시간을 포함하지 않는다"고 문서화한 시계다.
- **절전 감지는 오디오 데이터가 아니라 OS 시계로 한다** (eng review outside voice #2).
  - 절전을 포함하는 시계(macOS `CLOCK_MONOTONIC_RAW` = `mach_continuous_time`, Windows `QueryInterruptTime`)와 위 시계의 증가분 차이를 녹음 시작부터 잰다. 차이가 생긴 만큼이 절전 길이다. 두 쌍 모두 같은 원천에서 나온 시계라 깨어 있는 동안에는 차이가 변하지 않는다. macOS `CLOCK_MONOTONIC`은 쓰지 않는다. NTP가 속도를 조정해(실측 약 -3ppm) 깨어 있어도 차이가 조금씩 벌어진다. 두 시계를 차례로 읽는 오차가 있으므로 1초 미만의 차이는 절전으로 보지 않는다.
  - 그래서 마이크가 빠지고 시스템 오디오가 무음인 공백은 길이와 상관없이 절전으로 오판하지 않는다. 데이터 공백은 항상 장치 문제로 보고 아래 무음 채우기로 처리한다.
  - 기준 시계가 절전을 세지 않으므로, 절전 구간에는 어느 트랙에도 무음이 들어가지 않는다.
- 트랙마다 `기대 샘플 수 = 시계 경과 × 16000`을 계산한다.
  - 기록한 샘플이 기대보다 100ms(1,600샘플) 넘게 적으면, 차이만큼 0을 채운다. Windows 루프백의 무음 구간과 마이크 끊김이 이걸로 처리된다.
  - 10초마다 확인해서 기대보다 100ms 넘게 많으면, 넘친 만큼 버린다. 장치 클럭이 빠른 경우다.
- 절전 처리(REC-06): 위에서 잰 절전 길이가 5분 이하면 계속 녹음하고, 그 구간을 `meta.json`의 `gaps`에 남긴다. 5분을 넘으면 절전 시점에서 녹음을 닫고 `recorded`로 바꾼 뒤 대기열에 넣는다.

### 4.3 장치 관리 (REC-07)

**macOS 시스템 오디오는 cpal 루프백을 쓰지 않는다 (결정, 2026-10-14).** cpal 0.18.2는 출력 장치에 입력 채널이 **없을 때만** Core Audio tap을 연다. 출력 장치가 입력도 가진 경우(USB·블루투스 헤드셋 대부분)에는 오류 없이 그 장치의 **마이크**를 연다(cpal `macos/device.rs`에서 확인). 앱이 헤드폰을 권장하므로(REC-10) 이 경우가 흔하고, 그러면 "시스템 오디오" 트랙에 헤드셋 마이크가 녹음된다. 그래서 `macos_tap.rs`가 tap을 직접 만든다.

- `objc2-core-audio`로 **전역 모노 tap**을 만든다(`CATapDescription` `initMonoGlobalTapButExcludeProcesses`, 제외 프로세스 없음, `Unmuted`, `private`). 특정 출력 장치가 아니라 모든 프로세스의 출력을 받는다.
- 그 tap 하나만 담은 **비공개 aggregate 장치**를 만든다(드리프트 보정 켬). 사전 구성은 cpal `loopback.rs`를 따랐다.
- aggregate는 만든 프로세스에게 보이는 입력 장치라서, cpal `device_by_id`로 찾아 보통 입력 스트림으로 연다(실측: 모노 48kHz f32로 열림).
- 닫는 순서: 스트림 → aggregate 장치 → tap. 기본 출력 장치가 바뀌면 tap과 aggregate를 다시 만든다.
- macOS 14.2 이상이 필요하다(앱 최소 버전 14.6). 권한 문구는 `NSAudioCaptureUsageDescription`(11.1).
- macOS에서는 설정의 출력 장치 고정을 쓰지 않는다. 전역 tap은 모든 출력 장치의 소리를 받기 때문이다.
- Windows는 cpal WASAPI 루프백(기본 출력 장치에 입력 스트림)을 쓴다. 재생 중인 소리가 없으면 데이터가 오지 않고, 4.2의 무음 채우기가 메운다.

- `capture.rs`의 장치 감시 루프가 1초마다 `host.default_input_device()`와 `host.default_output_device()`의 `id()`(`DeviceId`)를 확인한다. cpal에는 기본 장치 변경을 구독하는 API가 없어 폴링한다. 스트림 오류 콜백도 플래그만 세우고, 다음 폴링(1초 이내)에서 다시 연다.
- 같은 장치가 3번 연속 열리지 않으면 그 장치는 5초마다만 다시 시도한다(macOS에서는 시도마다 tap을 만들고 지우기 때문). 처음 두 번은 1초 폴링을 따르므로 REC-07의 2초 안에 든다. 다른 장치가 기본 장치가 되면 바로 시도한다.
- 녹음이 끝난 뒤에는 캡처 스레드가 새 스트림이나 tap을 만들지 않고 경고도 보내지 않는다. 권한 팝업에 막혀 늦게 돌아온 경우도 같다. 앱 종료 때 이 스레드는 기다리지 않는다.
- 고정 장치는 `settings.json`의 `input_device`·`output_device`에 `DeviceId` 문자열(`coreaudio:<UID>` 등)로 둔다.
- 다시 연결하는 경우:
  - 스트림 오류 콜백이 왔다 (장치 분리).
  - 장치를 고정하지 않았는데 기본 장치 식별자가 바뀌었다 (헤드셋 연결 등).
  - 고정한 장치가 목록에서 사라졌다 → 기본 장치로 바꾼다.
- 다시 연결하는 동안 빠진 구간은 4.2의 무음 채우기 규칙으로 메운다.
- **대체할 장치가 없을 때**(예: 마이크가 하나뿐인 데스크톱에서 마이크를 뽑음): 녹음을 멈추지 않는다. 그 트랙은 무음으로 채우며 계속 녹음하고 "마이크를 찾을 수 없습니다" 배너를 띄운다. 장치가 다시 나타나면 1초 폴링이 붙인다. React에 `recording://warning` 이벤트를 보내 배너를 띄운다.

### 4.4 권한 감지 (REC-08)

- **첫 실행 권한 팝업은 스트림 생성을 멈춘다** (S1 도구에서 확인): 마이크 권한을 아직 묻지 않은 상태에서 cpal `build_input_stream`을 부르면, 사용자가 팝업에 답할 때까지 macOS HAL 안에서 호출이 돌아오지 않는다. 그래서 스트림은 캡처 스레드에서만 열고, UI와 IPC 스레드에서 열지 않는다. `start_recording`은 스트림을 기다리지 않고 바로 돌아온다. 장치 열기(macOS tap 생성부터 스트림 시작까지)가 1초를 넘으면 레벨 이벤트의 `waiting_permission`이 켜지고 화면에 "권한 허용을 기다리는 중"을 보여 준다. 그동안 두 트랙은 무음으로 채워져 시간축이 유지된다. "권한이 없으면 0 버퍼"는 사용자가 이미 거부한 뒤의 동작으로 보이며, S1에서 확인한다.

- 마이크: 마이크 장치에서 처음 받은 3초 분량의 샘플이 모두 정확히 0이면 `recording://warning { kind: "mic_permission" }`을 보낸다. 무음 채우기로 넣은 0은 세지 않는다.
- 시스템 오디오: 녹음 중에는 검사하지 않는다. 설정 오디오 탭의 "시스템 오디오 테스트"(M6)가 1kHz 사인파를 1초 재생하고, 같은 시간 루프백 RMS가 -40 dBFS를 넘으면 통과로 본다.
- **설정 오디오 탭의 테스트** (ONB-03, M6, `audio/check.rs`): 둘 다 녹음과 따로 장치를 열므로 녹음 중이면 거부하고, 도는 중에 녹음이 시작되면(⌘R·Ctrl+R, 독) 40ms 안에 멈추고 "녹음이 시작되어 테스트를 멈췄습니다"로 끝난다(시작할 때의 거부는 "녹음 중에는 테스트할 수 없습니다"). 녹음이 끝난 뒤에도 남는 결과가 아직 녹음 중처럼 읽히지 않게 문구를 나눴다. 시스템 오디오 테스트는 테스트음부터 멈춰 `system.wav`에 들어가지 않게 한다. 테스트는 앱 전체에서 한 번에 하나다(`AtomicBool`): 같은 장치를 두 번 열지 않고, 테스트 중에 설정 화면을 나갔다 다시 와도 둘째가 시작되지 않는다("이미 테스트 중입니다"). 장치 열기가 권한 팝업에 멈출 수 있어 blocking 스레드에서 돈다. 장치는 탭에 보이는 값(저장하지 않은 선택 포함)이고, 고른 장치가 연결돼 있지 않으면 기본 장치로 바꾸지 않고 실패한다. 다른 장치로 통과하면 안 되기 때문이다. 설정을 바꾸지 않으므로 저장 막대에 세지 않는다.
  - 시스템 오디오 테스트(`test_system_audio`): 듣기를 먼저 열고 테스트음을 낸다. 사인파는 최고 -20 dBFS(RMS -23 dBFS)이고 앞뒤 10ms를 페이드해 딸깍 소리가 나지 않는다. 테스트음을 연 직후 그때까지 들은 것을 버리고, 그 뒤 1.2초(테스트음 1초 + 출력·루프백 지연) 동안 들은 샘플 전체의 RMS로 판정한다. 버리지 않으면 테스트음 앞의 무음이 값을 묽히고, 출력 장치가 늦게 열리면 듣기 스트림의 2초 버퍼가 차서 테스트음이 버려진다. macOS는 녹음과 같은 전역 tap(4.3)을 하나 새로 만들어 듣는다. 제외한 프로세스가 없어 앱이 낸 테스트음도 들리므로 테스트음은 기본 출력 장치로 낸다. 권한이 없으면 0만 와서(-120 dBFS) 실패로 나온다. Windows는 탭의 출력 장치(없으면 기본)로 재생하고 그 장치의 WASAPI 루프백으로 듣는다. 재생 중인 다른 소리도 통과로 센다(앱이 시스템 오디오를 듣는다는 것은 같다). tap과 WASAPI 루프백은 출력 음량을 적용하기 전의 소리를 들을 가능성이 커(확인하지 않음) 실패 안내에 출력 음량을 넣지 않는다. 결과는 통과 여부만 돌려준다. 기준(-40 dBFS)과 듣는 시간은 무시한 테스트 `on_this_machine`이 실제 장치에서 찍는 dBFS로 맞춘다.
  - 마이크 테스트(`test_microphone`): 탭을 열 때는 마이크를 열지 않는다. 열면 설정 화면에서 권한 팝업이 뜬다. "테스트"를 누르면 5초 동안 열고 40ms마다 `audio-test://level`(0~100, 녹음 화면 미터와 같은 -60~0 dBFS)을 보낸다. 장치 버퍼가 오지 않은 40ms는 보내지 않아 막대가 0으로 깜빡이지 않는다. 40ms 하나라도 -50 dBFS(REC-05의 무음 기준) 이상이면 "소리가 들어와요"다. 권한을 아직 묻지 않았다면 이 버튼이 첫 권한 팝업을 띄울 수 있다(첫 녹음보다 먼저).
- macOS에서는 권한이 없으면 오류 없이 0 버퍼만 온다. 그래서 위 방식으로만 판정한다.

### 4.5 합산과 게이팅 (TRN-02)

전사 워커가 **구간마다** `mic.wav`와 `system.wav`에서 그 구간의 샘플을 읽어 `mix.rs`로 메모리에서 합친다. 합친 결과는 파일로 저장하지 않는다(eng review outside voice #5). 10분 구간은 f32로 약 38MB다.

```
for 각 20ms 프레임:
    sys_rms = RMS(system 프레임)
    target_gain = sys_rms > -45 dBFS ? -20 dB : 0 dB
    mic_gain = 스무딩(target_gain, attack 5ms, release 300ms)
    out = mic × mic_gain + system
    out = 소프트 리미터(out)   # 클리핑 방지
```

임계값(-45 dBFS), 감쇠(-20dB), attack·release 값은 **[S4]**에서 조정한다.

- 구현(`audio/mix.rs`): 목표 이득은 20ms 프레임마다 정하고, 실제 이득은 샘플마다 1차 스무딩(시상수 attack 5ms, release 300ms)으로 따라간다. 이득은 구간 사이에 이어지지 않고 구간마다 1에서 시작한다. 첫 300ms만 영향이 있어 무시한다.
- 소프트 리미터: |x| ≤ 0.5는 그대로, 그 위는 tanh 곡선으로 1.0에 다가가기만 하고 넘지 않는다.
- 두 WAV에서 같은 위치의 창을 `hound` seek로 읽는다. 길이는 두 트랙 중 짧은 쪽에 맞춘다.

4시간 녹음을 f32로 한꺼번에 메모리에 올리면 약 920MB이므로, 항상 창이나 구간 단위로만 읽는다. 처리 단계는 회의 폴더에 오디오를 새로 쓰지 않으므로, 디스크 부족으로 녹음이 끝난 직후에도 처리가 디스크를 더 쓰지 않는다(전사·요약 결과는 수십 KB).

### 4.6 디스크 공간 (REC-11, eng review D7)

- 필요량: 4시간 회의 기준 두 트랙 약 920MB. 처리 단계는 오디오를 새로 쓰지 않는다(4.5). 두 트랙 녹음 속도는 64KB/s다(16kHz × 2B × 2트랙).
- **시작 전**: 여유 공간이 1.5GB 미만이면 "남은 공간으로 최대 약 N분 녹음할 수 있습니다"(N = 여유 공간 ÷ 64KB/s) 경고를 띄운다. 녹음은 시작할 수 있다.
- **녹음 중**: 60초마다 여유 공간을 확인한다. 200MB 미만이 되거나 WAV 쓰기 오류가 나면 녹음을 안전하게 끝낸다. 마지막 flush, 상태 `recorded`, 처리 대기열에 넣기, "디스크 공간이 부족해 녹음을 종료했습니다" 알림 순서다.
- 단위 테스트: 쓰기 오류를 주입하면 상태가 `recorded`가 되고 WAV가 유효한지 확인한다.

  - 파일마다 3번까지 시도한다. 연결 실패·시간 초과·끊김만 다시 시도하고(이어받기), HTTP 오류와 해시 불일치는 바로 실패다. 실패해도 `.part`는 남아 다음 "받기"가 이어받는다.
  - 이어받을 때는 응답의 `Content-Range` 시작이 `.part` 크기와 같을 때만 덧붙인다. 다르면 `.part`를 지우고 처음부터 받는다. `Range`를 보냈는데 200(파일 전체)이 오면, `Content-Length`가 모델 크기와 같을 때만 `.part`를 비우고 받고, 아니면 실패로 보고한다. 크기가 다 찬 `.part`는 받지 않고 해시 검증부터 한다.
  - 진행률은 `model://download`로 약 1%마다 보낸다. 취소(`cancel_model_download`)는 다운로드 작업을 어디서 기다리든 바로 끊는다. 받은 만큼은 `.part`에 남고, 바로 직접 가져오기를 할 수 있다. 결과는 "모델 다운로드를 취소했습니다"다. 해시 확인(블로킹 작업)은 끊을 수 없어 끝까지 돌지만, 취소된 다운로드는 그 뒤로 파일 이름 바꾸기·삭제를 하지 않는다. 다운로드마다 취소 표시를 두고, 이름 바꾸기·삭제는 그 표시의 잠금 안에서 표시가 꺼져 있을 때만 한다. 취소도 같은 잠금 안에서 표시를 켠다.
  - 대기열이 시작할 수 있는지 볼 때는 크기만 확인한다. 크기가 맞아도 내용이 틀릴 수 있으므로 "받기"는 설치된 파일의 해시를 다시 확인하고, 틀리면 지우고 다시 받는다. 워커가 모델을 불러오지 못하면(종료 코드 3) 대기열이 두 파일의 해시를 확인한다. 틀린 파일은 지우고 "손상됐습니다. 다시 받아 주세요", 없거나 읽을 수 없으면 "없거나 읽을 수 없습니다. 다시 받아 주세요", 둘 다 맞으면 파일 문제가 아니므로(예: 메모리 부족) 다른 앱을 닫고 다시 시도하라고 안내한다. 다운로드·가져오기가 도는 동안에는 해시만 보고 지우지 않는다(그 파일을 설치하는 중일 수 있다).
- **직접 가져오기**: 녹음자가 고른 파일의 크기로 어느 모델인지 고르고(맞는 것이 없으면 거부), `{파일}.import`로 복사해 디스크에 내린(`sync_all`) 뒤 같은 방식으로 해시를 검증한다. 다운로드의 `.part`는 이어받기용으로 그대로 둔다. 다운로드 중에는 가져오기를 받지 않는다.
- **모델이 없을 때**: 대기열은 회의를 시작하지 않고 기다리게 둔다. 받기·가져오기가 끝나거나 설정을 저장하면 대기열을 다시 돌린다. 시작한 뒤에 모델이 없어졌으면 그 회의를 실패로 두지 않고 대기열 맨 앞에 돌려놓는다.
- **S3 실패 시 변화**: 내장 VAD가 없는 `whisper-rs` 버전으로 고정하면, VAD를 Silero ONNX 모델과 `ort` 크레이트로 따로 돌린다. 그러면 위 표의 VAD 항목이 ONNX 파일로 바뀌고 의존성에 `ort`가 추가된다.

### 5.2 구간 나누기와 실행

- **녹음 길이 (M2 → M3 인계)**: 녹음 길이는 `meta.json`의 `duration_ms`가 아니라 두 WAV 중 짧은 쪽의 길이(`min(len)`)로 정한다. 쓰기 오류로 끝난 녹음은 WAV가 마지막 5초 flush까지만 유효해 `duration_ms`보다 짧고, 중단된 녹음은 `duration_ms`가 0이다.

1. 워커를 `--plan-chunks` 모드로 한 번 띄운다. 워커는 두 트랙을 10분 창(앞 창과 30초 겹침) 단위로 읽어 메모리에서 합치고 `WhisperVadContext`로 음성 구간 목록을 얻은 뒤, 구간 경계를 JSON으로 출력한다. whisper/ggml 네이티브 코드는 모두 워커 안에서만 돈다. 이 API는 샘플 슬라이스 전체를 한 번에 받으므로, 4시간 녹음을 통째로 넘기면 f32로 약 920MB가 된다. 그래서 창 단위로 나눈다. 창마다 찾은 음성 구간을 모두 모아 겹치거나 맞닿은 구간을 하나로 합친다(합집합). 그래서 두 창이 함께 본 발화도, 창 끝에서 잘린 발화도 구간 하나가 된다.
2. 구간을 앞에서부터 자른다. 구간 끝은 시작에서 10분에 가장 가까운 무음 지점이다. 무음 지점은 음성 구간 사이(맨 앞·맨 뒤 포함)에서 음성 경계로부터 0.5초 떨어진 곳(무음이 1초보다 짧으면 가운데)이고, 시작에서 5~12분 사이만 본다. 그 안에 무음이 없으면 10분에서 자른다. 그래서 마지막 구간 말고는 5분보다 짧거나 12분보다 긴 구간이 없다. 길이는 벽시계 기준이라 구간 메모리가 12분(f32 약 46MB)을 넘지 않는다. 계획은 `chunks.json`에 한 번 저장하고, 재개할 때 다시 만들지 않는다.
3. 구간마다 워커를 띄워 Whisper를 실행한다. VAD상 음성이 0인 구간은 워커를 띄우지 않고 빈 결과로 둔다.
   - **VAD는 워커가 직접 한다.** whisper.cpp는 VAD 단계(음성만 잘라 이어 붙이기)를 `whisper_full` 안에서만 한다. whisper-rs 0.16의 `WhisperState::full`은 `whisper_full_with_state`를 불러 이 단계를 건너뛰므로, `enable_vad`만 켜면 무음과 잡음까지 전사한다(tiny 모델로 잡음을 넣으면 "MBC 뉴스 …입니다"가 나왔다). 그래서 워커가 같은 Silero 모델(기본 파라미터)로 구간의 음성을 찾고, whisper.cpp와 같은 방식으로 이어 붙인다(구간마다 뒤로 0.1초 더, 사이에 0.1초 무음). 세그먼트 시각은 원래 녹음 시각으로 되돌린다. 음성이 없으면 Whisper 모델을 불러오지 않는다.
   - 시각 되돌리기는 일부러 whisper.cpp와 다르다. whisper.cpp는 이어 붙인 오디오와 원래 오디오 사이를 선형으로 보간한다. 여기서는 음성 조각 안에서는 1:1로 옮기고, 조각 사이(잘라 낸 무음 자리)에 떨어진 시각은 가까운 발화 쪽으로 붙인다. 세그먼트 시작은 다음 조각의 시작으로, 끝은 앞 조각의 끝으로 간다. 그래서 세그먼트가 잘라 낸 무음만큼 일찍 시작하거나 늦게 끝나지 않는다.
   - 파라미터: `language="ko"`, 위의 VAD, `no_context=true`, `suppress_nst=true`, `temperature` 폴백 기본값 유지.
   - 샘플링은 beam search(beam 5)다. S2가 쓰는 `whisper-cli`의 기본값과 같아야 S2의 속도·정확도가 앱에 그대로 맞는다.
   - 스레드 수는 논리 CPU의 절반이다. 워커가 2개까지 동시에 돌기 때문이다(TRN-01). SMT 기기에서는 물리 코어 수, Apple Silicon에서는 코어의 절반이다. S2에서 측정해 조정한다.
   - 용어집을 initial prompt에 넣을지는 **[S2]**로 정한다. 지금은 넣지 않는다. S2에서 넣기로 하면 용어집을 워커 인자 하나로 더 넘겨 `set_initial_prompt`에 넣는다(Whisper는 앞쪽 약 224토큰만 쓴다).
4. 구간 결과(환각 필터를 거친 세그먼트)를 `transcript.partial.jsonl`의 한 줄로 저장한다. 형식: `{"chunk":3,"start_ms":...,"end_ms":...,"segments":[{"start_ms","end_ms","text"}]}`. 시각은 녹음 시작 기준 ms다. 파일에 덧붙이지 않고 매번 전체를 원자적으로 다시 쓴다(구간 24개 이하, 각 수 KB). 강제 종료가 반쯤 쓴 줄을 남기지 않게 하려는 것이다. `meta.json`의 `chunks_done`과 `backend`(마지막 구간을 처리한 장치)도 함께 고친다.
5. 마지막 구간이 끝나면 합쳐서 `transcript.json`을 쓰고 상태를 `transcribed`로 바꾼다. 형식: `{"segments":[{"start_ms","end_ms","text"}]}` (모든 구간의 세그먼트를 순서대로). 요약(M4)은 이 파일을 읽는다.

**재개 단위는 구간이다.** 재개할 때는 `transcript.partial.jsonl`의 마지막 구간 다음부터 처리한다. 줄의 구간 번호와 경계가 `chunks.json`의 다음 구간과 맞는 데까지만 믿고, 맞지 않는 줄부터는 다시 처리한다.

### 5.3 전사 워커 프로세스와 중단 (TRN-06, TRN-09)

전사는 **같은 실행 파일을 자식 프로세스로 띄워** 돌린다(eng review D5). whisper.cpp가 GPU 드라이버 문제 등으로 비정상 종료해도 앱, 녹음, UI는 살아 있다.

```
queue.rs ──spawn── 앱 실행 파일 --transcribe-worker {회의 폴더} {시작 ms} {끝 ms} {gpu|cpu} {모델} {VAD 모델}
   ▲                    │ stdout: JSON 한 줄씩
   │                    │   {"type":"progress","pct":42}
   │                    │   {"type":"result","device":"gpu","segments":[{"start_ms","end_ms","text"}]}
   └──── 종료 코드 ─────┘ 0 = 정상, 그 외 = 실패/크래시

queue.rs ──spawn── 앱 실행 파일 --plan-chunks {회의 폴더} {VAD 모델}
                        │   {"type":"progress","pct":10}
                        │   {"type":"plan","len_ms":...,"chunks":[{"start_ms","end_ms","speech_ms"}]}
```

- 워커 인자는 회의 id 대신 경로를 받는다. 워커는 Tauri 앱을 띄우지 않으므로 앱 데이터 폴더를 알 수 없고, 알 필요도 없다. `main.rs`가 Tauri 빌더보다 먼저 인자를 보므로 워커는 창을 열지 않고 단일 실행 검사에도 걸리지 않는다.
- `result`의 `device`는 실제로 돈 장치다. GPU 컨텍스트를 만들지 못하면 워커가 CPU로 바꿔 `cpu`를 보낸다(5.4).
- 워커는 stdin을 읽고 있다가 닫히면(앱이 크래시·강제 종료됨) 바로 끝난다. 자식 프로세스는 부모가 죽어도 남기 때문에, 이게 없으면 다시 켠 앱의 새 워커 옆에서 남은 워커가 GPU와 메모리를 계속 쓴다.
- Windows는 `CREATE_NO_WINDOW`로 띄워 콘솔 창이 뜨지 않게 한다.
- 워커는 결과 줄을 출력한 뒤 stdout을 비우고 소멸자 없이 바로 끝난다(macOS `_exit`, Windows `process::exit`). Metal·Vulkan 정리 단계의 크래시가 이미 보낸 결과를 지우고 `gpu_failed`를 남기지 않게 하려는 것이다. stdin 감시로 끝날 때도 같다.
- **무응답 감시**: 워커가 stdout에 5분 동안 한 줄도 내지 않으면 부모가 kill하고 크래시로 센다(5.4의 GPU 재시도 대상). 워커는 Whisper 창(30초 분량)마다, 구간 나누기는 10분 창마다 진행률을 낸다. 874MB 모델 로딩도 수 초다.
- 부모는 stdout을 바이트로 읽어 한 줄씩 JSON으로 해석한다. 우리 줄이 아니거나 UTF-8이 아닌 줄은 건너뛴다. stdout이 닫힌 뒤에도 프로세스가 실제로 끝날 때까지는 kill할 수 있게 둔다.

- **동시 실행** (TRN-01, 사용자 결정 2026-10-14): 워커 프로세스는 회의 2개까지 동시에 돈다. 나머지 회의는 대기열에서 들어온 순서(FIFO)대로 기다리고, 화면에 대기 순서를 보여 준다. 워커마다 모델을 따로 올리므로 메모리 사용이 두 배다. 8GB 기기에서 문제가 되는지 파일럿에서 본다.
- 워커는 구간 하나를 처리하고 끝난다. 모델 로딩(수 초)은 구간마다 반복되지만, 구간이 10분 분량이라 비중이 작다.
- 결과는 부모(`queue.rs`)가 받아 `transcript.partial.jsonl`에 쓴다. 워커는 회의 폴더의 오디오를 읽기만 한다.
- **중단**: 녹음이 시작되면 부모가 실행 중인 워커 프로세스를 모두 kill한다. 그 구간의 결과는 버리고, 녹음이 끝나면 회의마다 그 구간부터 다시 처리한다. abort 콜백에 기대지 않는다. kill하기 전에 "멈춘 이유"(녹음, 삭제, 종료)를 먼저 기록하므로 kill은 크래시로 세지 않는다. 멈춘 회의는 `paused`로 기록하고 대기열 맨 앞으로 돌아간다(원래 순서대로). 워커 스레드가 끝나기 전에는 같은 회의를 다시 시작하지 않는다.
- 워커의 stderr는 회의 폴더의 `worker.log`에 덧붙인다(크래시 원인 확인용). 실행마다 `--- {인자} ---` 줄을 먼저 쓴다. 실패 원인으로는 그 머리줄을 뺀 마지막 줄을 보여 준다.
- **종료 코드 계약**: `0` 정상, `2` 입력·파일 오류(오디오 없음, 인자 오류), `3` 모델 로드 실패(파일 손상·경로 오류), 그 외 코드나 시그널 종료는 **크래시**. 5.4의 GPU 실패 판정은 크래시(무응답 감시로 kill한 것 포함)만 센다. `2`·`3`은 GPU와 무관하므로 바로 `transcribe_failed`로 바꾸고 원인을 보여준다(`3`이면 해시를 확인해 "모델 다시 받기" 또는 메모리 안내, 5.1).
  - 대기열이 보내지 않은 SIGKILL(macOS 메모리 부족 시 OS가 보냄)은 크래시로 세지 않는다. 그 회의만 `transcribe_failed`로 바꾸고 "메모리가 부족해 전사가 중단되었습니다"를 보여 준다. `gpu_failed`는 쓰지 않는다.

### 5.4 백엔드 선택과 크래시 판정 (TRN-05, TRN-06)

- **빌드**: macOS는 `metal`, Windows는 `vulkan` feature로 빌드한다. CPU 사용은 런타임에 `WhisperContextParameters::use_gpu(false)`로 고른다.
- **Vulkan 로더 동봉**: Vulkan 빌드는 `vulkan-1.dll`에 로드 타임 의존성이 있다. 이 DLL이 없는 PC에서는 앱이 아예 시작되지 않는다. 그래서 LunarG Vulkan Loader(Apache-2.0)의 `vulkan-1.dll`을 실행 파일 옆에 함께 설치한다. `src-tauri/tauri.windows.conf.json`의 `bundle.resources`(`"vulkan-1.dll": "vulkan-1.dll"`)로 NSIS가 `$INSTDIR`(실행 파일 옆)에 설치하고, 제거할 때 지운다. 원본은 CI가 Vulkan SDK 1.4.313.2의 런타임에서 `src-tauri/vulkan-1.dll`로 복사한다(11.3). 실제 Windows PC에서는 첫 Actions 실행 뒤에 확인한다.
- **자동 선택 순서**:
  1. `settings.json`에 `gpu_failed=true`가 있으면 CPU를 쓴다.
  2. GPU 컨텍스트 생성을 시도하고, 실패하면 CPU로 바꾼다. GPU 장치가 아예 없으면 whisper.cpp가 스스로 CPU로 돈다. 이 경우 워커는 `gpu`로 보고하므로 `meta.json`의 `backend`가 실제와 다를 수 있다.
- **강제 설정**: 설정에서 백엔드를 "GPU"로 바꾸면 `gpu_failed`를 `false`로 되돌린다. "CPU"로 바꾸면 항상 CPU를 쓴다. "GPU"일 때는 `gpu_failed`와 상관없이 구간마다 GPU로 시작한다.
- **`gpu_failed`는 대기열이 쓴다**: 설정 화면의 저장(`save_settings`)은 저장돼 있던 `gpu_failed` 값을 그대로 두고, 백엔드가 "GPU"로 바뀔 때만 `false`로 만든다. 설정 화면이 대기열이 쓴 값을 예전 값으로 덮어쓰지 않게 하려는 것이다. 대기열은 `mark_gpu_failed`로 따로 쓴다.
- 장치는 구간마다 설정을 다시 읽어 정한다. 그래서 한 회의가 `gpu_failed`를 쓰면 함께 돌던 다른 회의도 다음 구간부터 CPU를 쓴다.
- **GPU 워커 크래시** (5.3 종료 코드 계약의 "크래시", 또는 kill하지 않았는데 결과 없이 끝남):
  - 같은 구간을 GPU 워커로 **한 번** 즉시 다시 실행한다.
  - 다시 비정상 종료하면 `settings.json`에 `gpu_failed=true`를 쓰고, 녹음자에게 "GPU 처리가 불안정해 CPU로 전환했습니다. 처리 시간이 길어집니다" 알림을 띄운 뒤, 같은 구간을 CPU 워커로 처리한다. 알림은 `transcribe://gpu-failed` 이벤트(앱 안 배너)다. 열 회의가 없어 OS 알림은 보내지 않는다(10.1, 11.1).
  - CPU 워커까지 비정상 종료하면 회의를 `transcribe_failed`로 바꾸고 원인(`worker.log` 마지막 줄)을 보여준다.
  - 앱 재시작은 필요 없다. 크래시 횟수는 처리 중 메모리에만 둔다.
- **비정상 결과 검사** (TRN-07): 환각 필터를 거친 구간 결과가 아래 중 하나면 그 구간을 CPU로 한 번 다시 처리한다. GPU 결과에만 한다. CPU 결과는 다시 돌려도 같으므로 이상해 보여도 그대로 쓴다.
  - VAD상 음성이 30초 넘게 있는데 전사 텍스트가 비어 있다.
  - 같은 토큰이 8번 넘게 연속으로 반복된다. 토큰은 Whisper 토큰이 아니라 공백으로 나눈 낱말(문장부호 제거)이다. 띄어쓰기 없이 반복되는 말("아아아아…")은 잡지 못한다.

### 5.5 환각 필터 (TRN-08)

- 세그먼트 텍스트를 정규화한다: 앞뒤 공백 제거, 문장부호 제거, 연속 공백을 하나로. 문장부호는 글자·숫자·공백이 아닌 모든 문자다(전각 문장부호, 따옴표, "…", "♪" 포함).
- 정규화한 텍스트가 `src-tauri/src/resources/hallucinations.ko.txt`의 한 줄과 **정확히 같을 때만** 그 세그먼트를 버린다. 정규화하면 빈 문자열이 되는 세그먼트("♪", "...")도 버린다. 낱말이 없어 전사본에 남길 내용이 없기 때문이다.
- 목록은 빌드에 넣는다(`include_str!`). 파일럿 동안 새 버전은 설치 파일로 나가므로, 목록 수정도 새 빌드로 나간다. `#`로 시작하는 줄과 빈 줄은 무시한다.
- 초기 목록 예: `시청해주셔서 감사합니다`, `구독과 좋아요 부탁드립니다`, `다음 영상에서 만나요`. 파일럿에서 발견되는 대로 추가한다.

## 6. 요약

### 6.1 요청

- `POST {base_url}/chat/completions`(`base_url` 끝의 `/`는 뗀다), `temperature: 0.2`, `max_tokens`(6.3). 메시지는 시스템 프롬프트(6.2)와 사용자 메시지 하나다. 응답은 `choices[0].message.content`를 쓴다.
- `Authorization: Bearer {api_key}`는 키체인에 키가 있을 때만 보낸다. 로컬 Ollama·LM Studio는 키가 필요 없다. 키는 요청 직전에 Rust 안에서만 읽는다(9.2).
- **프록시를 거치지 않는 요청**: 로컬 연결(`is_local=true`)과 loopback 주소(`localhost`, `*.localhost`, `127.0.0.0/8`, `::1`)로 가는 요청은 OS·환경 변수의 HTTP 프록시를 쓰지 않는다. 그러지 않으면 "로컬로 요약"한 전사본이 사내 프록시로 평문 전송된다(SUM-08). hyper-util은 macOS 프록시 예외 목록을 읽지 않고, Windows의 `<local>`은 `localhost`와 맞지 않아 OS 설정에 기댈 수 없다. 클라우드 연결은 프록시를 그대로 쓴다.
- **추론 모델 호환**: OpenAI 추론 모델은 `max_tokens`와 기본값이 아닌 `temperature`를 400으로 거부한다. 400 응답 본문에 `max_completion_tokens`가 있거나, `max_tokens`·`temperature`를 지원하지 않는다는 말("unsupported", "not supported")이 있으면 호환 요청으로 한 번 다시 보낸다. 호환 요청은 `temperature`를 빼고(`reasoning_effort`도 보내지 않는다) `max_completion_tokens = max_tokens + 8,000`을 쓴다. 추론 모델은 생각에 쓴 토큰도 이 한도에서 빼기 때문이다. 6.3의 예산 검사는 이 8,000을 세지 않는다. 추론 모델은 컨텍스트가 커서(수십만 토큰) 문제가 되지 않는다고 본다. 한 번 알게 되면 그 요약의 나머지 요청도 이 형식으로 보낸다. 호환 요청에 다시 400이 오면 공급자 오류다.
- 답에서 마지막 `</think>`까지는 로컬 추론 모델의 생각이라 버린다. 채팅 템플릿이 `<think>`를 미리 열어 두는 모델(R1, QwQ)은 내용이 여는 태그 없이 생각으로 시작하므로, 태그가 어디에 있든 마지막 닫는 태그 뒤만 답이다. 닫히지 않은 `<think>`로 시작하면 생각뿐이다.
- 답이 잘렸으면(`finish_reason: "length"`) 요약이 아니라 공급자 오류다("요약이 길이 제한에서 잘렸습니다. 컨텍스트 토큰 설정을 확인해 주세요"). 생각을 버린 뒤 답이 비었어도 공급자 오류다(6.4).
- **입력 잘림 감지**: Ollama의 `/v1`은 요청마다 컨텍스트를 받지 않고 서버의 `num_ctx`(`OLLAMA_CONTEXT_LENGTH`)를 쓰며, 넘친 입력을 말없이 자른다. LM Studio도 모델을 불러올 때 정한 Context Length를 쓴다. 그래서 응답에 `usage.prompt_tokens`가 있고 그 값이 보낸 입력 글자 수 ÷ 4보다 작으면(영어도 한 토큰이 약 4자라 그보다 적게 읽을 수 없다) "LLM 서버가 입력을 잘랐습니다. 서버의 컨텍스트 길이(Ollama: OLLAMA_CONTEXT_LENGTH, LM Studio: 모델 로드 시 Context Length)를 연결 설정의 컨텍스트 토큰 이상으로 맞춰 주세요"로 실패한다. `usage`가 없으면 확인하지 않는다.
- **시간 제한** (eng review D12): 연결 10초, 응답 전체 300초(클라우드) / 900초(로컬). 연결마다 `timeout_secs`로 바꿀 수 있다. 넘으면(연결 10초 포함) 6.4의 "시간 초과"이고, 다른 네트워크 오류와 따로 "LLM 응답 시간 초과입니다. 연결을 확인하고 다시 실행해 주세요"를 보인다.
- 연결 정보는 여러 개 저장할 수 있다(예: "회사 클라우드", "내 Ollama"). 각 연결은 `settings.json`에 `name`, `base_url`, `model`, `context_tokens`, `is_local`, `timeout_secs`를 두고, `api_key`는 키체인에 둔다. `context_tokens`는 새 연결의 기본값이 8,192이고, 쓰는 모델의 실제 컨텍스트 길이로 바꿔 입력한다. 너무 작게 잡으면 구간 요약(6.3)이 늘어나고, 긴 회의를 나눠야 할 때 약 3,900보다 작으면 "컨텍스트 토큰 설정이 너무 작습니다"로 실패한다(6.3). 로컬 서버는 이 값을 서버의 컨텍스트 설정보다 크게 잡으면 서버가 입력을 자른다(위의 입력 잘림 감지).
- **쓰는 연결** (`summarize::route`, `summary_route`도 같은 함수를 쓴다):
  1. `meta.json`의 `llm_connection`이 있으면 그 연결이다. 다시 실행(`retry_summary`)에서 고른 연결이나 앞서 요약을 시작할 때 정한 연결이다. 그 이름의 연결이 없으면 실패("LLM 연결 '{이름}'을(를) 찾을 수 없습니다").
  2. "로컬로 요약"(`summarize_local`)이 켜져 있으면 기본 연결(`default_llm`)이 로컬일 때 그것, 아니면 목록에서 첫 번째 `is_local=true` 연결이다. 로컬 연결이 없으면 실패("로컬 LLM 연결이 없습니다"). 녹음자가 전사본을 PC 밖으로 내보내지 않겠다고 고른 것이라 클라우드로 대신 보내지 않는다.
  3. 그 밖에는 기본 연결, 기본 연결이 없거나 목록에 없으면 첫 번째 연결이다.
  - 연결이 하나도 없으면 실패("LLM 연결이 없습니다. 설정에서 추가한 뒤 다시 실행해 주세요"). 단, 전사가 막 끝난 회의는 실패하지 않고 `transcribed`에서 기다린다(8.4).
- 새 회의의 `summarize_local`은 녹음을 시작할 때 설정의 `summarize_local_by_default`로 정한다. 로컬 연결이 하나도 없으면 토글을 보여주지 않는다(SUM-08). 토글(`set_summarize_local`)은 요약이 시작되기 전까지만 바꿀 수 있다. 시작되면(`llm_connection`이 정해졌거나 `transcribed`·`paused` 다음 단계로 갔으면) 잠긴다.
- 요약을 시작할 때 `meta.json`에 `summarizing`과 함께 고른 연결의 이름(`llm_connection`)과 로컬 여부(`summarize_local`)를 쓴다. 그래서 멈췄다가 다시 요약해도 같은 연결로 가고, 회의 문서의 메타 줄이 "{공급자}로 보내 요약함"을 보일 수 있다(SUM-07).
- 요약은 처리 스레드가 띄운 비동기 작업 하나다(구간 요약까지 모두 포함). 처리 스레드는 그 작업을 기다리고, 대기열은 작업의 abort 핸들을 들고 있다. 녹음이 시작되면 `is_local=true`인 연결의 요약 작업만 abort한다(SUM-09). 클라우드 요약은 녹음 중에도 끝까지 간다. 삭제와 앱 종료는 클라우드 요약도 abort한다(8.3, 8.5). 작업은 대기열 잠금 안에서 시작하고 그때 "클라우드 요약" 표시를 함께 단다. 같은 잠금 안에서 멈춘 이유를 먼저 확인하므로, 바로 앞에 시작한 녹음을 놓치지 않는다.

### 6.2 프롬프트

시스템 프롬프트(`summarize.rs`의 `SYSTEM`):

```
너는 회의록 작성자다. 한국어 회의 전사본을 읽고, 회의에 없던 사람이 읽을 요약을 쓴다.
출력은 아래 Markdown 형식만 쓴다.

# {회의 제목: 20자 이내}
## 결정사항
- ...
## 액션 아이템
- [담당자] 할 일 (기한)
## 주요 논의
- ...
## 미해결 질문
- ...

규칙:
- 전사본에는 말한 사람 표시가 없다. 전사본에 명시되지 않은 담당자나 기한은 "미정"으로 쓴다. 추정하지 않는다.
- 해당 내용이 없는 섹션은 "- 없음"으로 쓴다.
- 결정사항에는 회의에서 정한 것만 쓴다. 기각된 제안과 "~하지 않기로" 한 것은 결정사항이 아니다. 필요하면 주요 논의에 쓴다.
- 회의 중에 결정이 바뀌었으면 마지막 상태만 결정사항에 쓴다.
- 전사 오류로 보이는 단어는 문맥상 확실할 때만 고친다.
- 용어집의 표기를 따른다: {용어집}      ← 용어집이 비어 있으면 이 줄을 넣지 않는다
```

- 결정사항 두 규칙은 eval의 내용 검사(12.3)가 보는 것이다: 기각된 제안, 부정문, 뒤집히기 전 결정이 결정사항에 나오면 실패다.
- 사용자 메시지는 한 줄 안내 + 빈 줄 + 내용이다. 내용은 전사본이면 세그먼트 텍스트를 한 줄에 하나씩(시각 없이), 부분 요약을 합칠 때는 부분 요약들을 `---` 줄로 나눠 넣는다. 안내는 셋 중 하나다: 전사본 전체("회의 전사본이다."), 전사본의 한 구간("…한 구간이다. 이 구간만 같은 형식으로 요약한다."), 부분 요약 합치기("…같은 형식의 요약 하나로 합친다. 겹치는 내용은 한 번만 쓰고, 앞에서 정한 것이 뒤에서 바뀌었으면 마지막 상태만 결정사항에 쓴다.").
- LLM이 쓴 첫 줄 `# 제목`은 `meta.title`이 되고, 회의 문서의 요약 본문에서는 빠진다. `summary.generated.md`에는 제목 줄까지 LLM이 쓴 그대로 남긴다(SUM-05).

### 6.3 긴 회의 (SUM-04)

- 토큰은 **글자 하나에 한 토큰**으로 추정한다(공백·문장부호까지 모든 글자). 처음에는 `글자 수 ÷ 2`를 보수적이라고 적었지만, 실제 토크나이저(Llama, Qwen, cl100k)에서 한국어는 글자당 약 0.6~1.0토큰이라 ÷2는 오히려 낙관적이었다. 입력 추정에는 시스템 프롬프트와 사용자 메시지(안내 포함)를 모두 센다.
- 입력 추정이 연결의 `context_tokens`의 60% 이하면 요청 하나로 끝낸다. 넘으면 전사본을 줄 경계에서 구간으로 나눈다. 각 구간에 같은 형식의 부분 요약을 만들고, 부분 요약들을 합쳐 최종 요약을 만든다.
- **모든 요청에 예산을 둔다** (eng review outside voice #8). 요청마다 `입력 추정 + max_tokens ≤ context_tokens × 0.9`를 지킨다. 부분 요약의 `max_tokens`는 1,500, 최종 요약은 `min(4,000, 남은 예산)`이다. 구간은 이 예산에 맞을 만큼 줄을 앞에서부터 채운다. 한 줄이 구간 하나보다 길면 글자 단위로 자른다.
- 부분 요약들을 합친 입력이 60% 이하이거나, 60%는 넘어도 요청 하나에 다 들어가면(`입력 추정 + 1,500 ≤ 예산`) 바로 최종 요약을 만든다. 한 번 더 축약해 봐야 최종 요약에 요약 하나를 넘길 뿐이기 때문이다. 이때 최종 요약의 `max_tokens`도 `min(4,000, 남은 예산)`이라 1,500 이상이다.
- 요청 하나에 다 들어가지 않으면, 이웃한 것끼리 예산 안에 들어가는 만큼 묶어 한 번 더 요약하는 단계를 들어갈 때까지 반복한다(재귀 축약). 묶음은 순서를 지키므로 "마지막 상태" 규칙(6.2)이 유지된다. 하나만 든 묶음은 다시 요약하지 않고 그대로 다음 단계로 넘긴다. 요약을 혼자 다시 요약하면 내용만 줄기 때문이다.
- **끝이 보장된다**: 한 단계가 부분 요약 수를 줄이지 못하면(둘씩도 묶이지 않으면) 실패한다. 요청 하나가 부분 요약 하나(1,500토큰 = 1,500자)도 담지 못할 만큼 컨텍스트가 작으면 요청을 보내기 전에 바로 실패한다. 둘 다 "컨텍스트 토큰 설정이 너무 작습니다"이고, 설정에서 모델의 실제 컨텍스트 길이를 넣으라고 안내한다. 기본값 8,192는 충분하고, 나눠야 하는 긴 회의에서 약 3,900 미만(용어집이 길면 조금 더)이면 바로 실패한다.
- 로컬 서버가 이 예산과 다른 컨텍스트로 돌면 입력을 말없이 자를 수 있다. 응답의 `usage.prompt_tokens`로 잡는다(6.1 입력 잘림 감지).
- 부분 요약 중 하나라도 실패하면 요약 전체를 실패로 처리한다(SUM-06).
- 진행률은 요청 수로 센다: 끝난 요청 / 지금까지 알려진 요청(구간 수 + 최종 1, 재귀 축약 단계가 생기면 그만큼 늘어난다). `meeting://progress`의 `chunk`/`chunks`다(10.2).

### 6.4 실패 분류 (SUM-06)

| 상황 | 판정 | 화면 메시지 |
|---|---|---|
| 클라우드 연결인데 키체인에 키가 없음 (요청 전에 확인) | 키 미설정 | 설정에서 API 키 입력 |
| 연결 실패, 연결이 끊김 | 네트워크 | 인터넷 연결 확인 (오류 내용 함께) |
| 시간 초과 (연결 10초, 응답 전체 `timeout_secs`) | 네트워크 (시간 초과) | "LLM 응답 시간 초과입니다. 연결을 확인하고 다시 실행해 주세요" |
| `is_local`이고 연결 거부 | 로컬 LLM 미실행 | Ollama·LM Studio 실행 확인 |
| 401, 403 | 키 문제 | 설정에서 API 키 확인 |
| 429 | 할당량 | 잠시 후 다시 시도 |
| 그 외 4xx, 5xx | 공급자 오류 | 응답 본문 일부 표시(200자까지, 본문에 키가 있으면 `***`로 가림) |
| 2xx인데 답이 잘림(`finish_reason: "length"`), 비었음, 해석할 수 없음 (6.1) | 공급자 오류 | "요약이 길이 제한에서 잘렸습니다…", "빈 요약을 받았습니다(finish_reason: …)", "응답을 해석할 수 없습니다: {본문 일부, 키는 가림}" |

- 연결 거부는 오류의 원인 사슬에서 `ConnectionRefused`를 찾아 판정한다. 클라우드 연결의 연결 거부는 네트워크 오류다.
- 자동 재시도는 네트워크 오류(시간 초과 포함)에 한해 1번만 한다. HTTP 오류와 2xx의 잘림·빈 답은 다시 보내지 않는다(6.1의 호환 재시도만 예외). 시간 제한 값은 6.1, 7.1, 5.1에 있다. 응답하지 않는 로컬 스텁 서버로 응답 시간 제한이 "시간 초과"로 분류되고 정확히 한 번 더 시도하는지, 요청을 읽고 답 없이 끊는 서버가 네트워크 오류로 정확히 한 번 더 시도되는지 단위 테스트한다.
- 실패하면 상태는 `summarize_failed`, 메시지는 `meta.json`의 `error`다. 전사본은 그대로다. 다시 실행(`retry_summary`)은 연결을 골라 대기열에 넣는다(10.2).

### 6.5 빈 전사본 (SUM-10, eng review D8)

- 환각 필터를 거친 전사본이 30자 미만(공백 제외)이면 LLM을 부르지 않는다. 빈 입력에서 LLM이 회의 요약을 지어내는 것을 막고 API 비용도 아낀다. 연결을 고르지 않고 키도 읽지 않는다.
- 상태는 `review`로 두고 `meta.json`의 `no_speech`를 `true`로 쓴다. `summary.generated.md`는 만들지 않는다. 회의 문서는 `no_speech`를 보고 "음성이 거의 감지되지 않았습니다"를 보여준다. 보내기 막대는 띄우지 않고, 삭제와 "전송 안 함"만 남긴다.
- 단위 테스트: 30자 경계, 그리고 짧은 전사본의 회의가 스텁 LLM에 연결 하나 없이 `review` + `no_speech`가 되는지 확인한다. 안내 표시는 회의 문서 테스트(Vitest)다.

## 7. Slack 전송

### 7.1 페이로드

```json
{
  "text": "{제목} 회의 요약",
  "blocks": [
    { "type": "markdown", "text": "**{제목}**\n{일시} · {길이} · 녹음: {녹음자}\n\n{요약 본문}" },
    { "type": "context", "elements": [
      { "type": "mrkdwn", "text": "AI 요약 · 녹음자 검토 완료 (수정 {N}곳)" }
    ]}
  ]
}
```

- `text`는 알림 미리보기용 대체 텍스트다. mrkdwn으로 읽히므로 제목의 `&` `<` `>`를 이스케이프한다. LLM이 쓴 제목의 `<!channel>`이 멘션이 되지 않게 하려는 것이다.
- **멘션 무력화**: `markdown` 블록이 `<!here>`, `<!channel>`, `<@U…>`, `<#C…>`를 멘션으로 읽는지 Slack 문서는 말하지 않는다. 그래서 제목·녹음자 이름·본문의 `<!`, `<@`, `<#`는 `<` 바로 뒤에 U+200B(폭 없는 공백)를 넣어 글자로 남긴다. `slack::markdown`이 머리말과 본문을 합친 뒤에 넣으므로 `slack_length`가 세는 글자(12,000자 검사 포함)가 곧 보내는 글자다(넣은 만큼 늘어난다). 대체 경로는 이것을 다시 `&lt;`로 이스케이프하고, `text`에는 이스케이프로 `<`가 남지 않는다. 링크 모양의 `[x](!here)`를 `markdown` 블록이 어떻게 보이는지는 수동 점검으로 확인한다(로드맵 M5).
- **머리말**: `{제목}`은 저장된 한 줄 제목(`store::one_line`, 비었으면 "제목 없음"). `{일시}`는 회의 시작(`created_at`)의 녹음자 현지 시각으로 `2026-10-13 (화) 14:00` 형식이다. Rust는 현지 시차를 안전하게 읽지 못하므로(8.2) 웹뷰가 그 시각의 시차를 분으로 넘긴다(`-new Date(created_at).getTimezoneOffset()`, 서머타임도 맞는다). `{길이}`는 `duration_ms`로 "1시간 5분", "2시간", "42분", 1분이 안 되면 "1분 미만"이다. `{녹음자}`는 설정의 `recorder_name`이고, 비어 있으면 " · 녹음: …"를 통째로 뺀다.
- 요청 시간 제한은 연결 10초, 요청 전체 15초다(eng review D12). 클라우드 요청이라 시스템 프록시를 그대로 쓴다. 단 loopback 주소는 LLM 요청과 같이 프록시를 거치지 않는다(6.1). **리다이렉트는 따라가지 않는다**(`redirect::Policy::none`): 따라가면 사내 프록시·SSO 게이트웨이의 302 뒤 로그인 페이지가 준 200을 성공으로 볼 수 있고, 다른 호스트로 가는 요청의 Referer에 웹훅 URL이 실린다. 3xx는 아래 "확인하지 못함"이다.
- `markdown` 블록의 `text`(머리말 + 본문) 길이(`chars().count()`)가 12,000자를 넘으면 전송하지 않는다(REV-02). 기준은 하나다: 회의 문서의 글자 수도 `slack_length` 명령으로 같은 함수(`slack::markdown`)가 만든 텍스트를 센다. 꼬리말은 별도 `context` 블록이라 세지 않는다.
- **웹훅 URL**: 전송 직전에 Rust 안에서만 키체인(`slack:{이름}`)으로 읽는다(9.2). URL 자체가 비밀값이라 돌려주지도, 로그에 쓰지도, 오류 문구에 넣지도 않는다. 응답 본문은 Slack의 오류 코드 모양(앞뒤 공백을 뺀 본문이 `^[a-z_]{1,64}$`, 예: `no_service`)일 때만 문구에 쓰고, 그 밖의 본문(프록시의 HTML 페이지 등)은 쓰지 않고 `HTTP {코드}`만 보인다. URL은 경로만, 잘린 채, JSON 이스케이프나 퍼센트 인코딩으로도 되돌아올 수 있어 원문 그대로만 가려서는 막지 못하기 때문이다. 네트워크 오류는 reqwest의 URL을 뺀 가장 안쪽 원인만 보인다. `https://`만 받는다. 평문 `http://`는 `localhost`와 loopback IP(`127.0.0.0/8`, `::1`)로 가는 주소만 받는다(시험용 스텁). `*.localhost`는 받지 않는다(이름 해석이 밖으로 보낼 수 있다). LLM 요청의 프록시 우회 판정(6.1)은 `*.localhost`도 그대로 포함한다.
- **[S5] 대체 경로는 실행 중에 자동이다** (M5): 먼저 `markdown` 블록으로 보낸다. 웹훅이 400에 `invalid_blocks`(또는 `markdown` 블록을 말하는 본문)로 답하면 **한 번만** `section` 블록 + mrkdwn으로 다시 보낸다. 변환: `**굵게**` → `*굵게*`, 제목(`#`~`######` + 공백) → 굵은 한 줄(안의 `**`는 뺀다), `[text](url)` → `<url|text>`(`url`이 `https://`, `http://`, `mailto:`로 시작할 때만. `[담당](!here)`, `[x](@U…)`, `[x](!subteam^…)`는 바꾸면 멘션이 되므로 이스케이프한 글자 그대로 둔다. `[담당자]`처럼 링크가 아닌 대괄호도 그대로), `&` `<` `>` 이스케이프(링크의 `&`도 `&amp;`로, Slack이 되돌린다). 줄 경계에서 3,000자 이하로 section 블록을 나누고, 3,000자보다 긴 한 줄은 글자 단위로 자른다. 꼬리말은 같다. 그래서 스파이크 S5는 실제 Slack이 어느 경로를 타는지 확인만 한다.
- **실패 분류** (SND-06). **성공은 200에 본문 `ok`(앞뒤 공백 무시)뿐이다.** 상태 코드로 먼저 가른다: 200 뒤에 본문을 읽지 못하면 확인하지 못한 것이고, 실패 코드는 본문을 읽지 못해도 그 코드의 실패다. 아무것도 가지 않았다고 확신할 수 있는 것은 연결 실패(`is_connect`)뿐이라, 그 밖의 오류는 모두 채널을 확인하라고 한다. 아래에서 `{코드}`는 본문이 오류 코드 모양일 때만 붙는다(위 웹훅 URL).

| 상황 | 화면 메시지 |
|---|---|
| 키체인에 웹훅 URL이 없음 (요청 전) | "웹훅 주소가 없습니다. 설정 → Slack에서 웹훅 주소를 입력해 주세요" |
| `https://`가 아니거나 URL이 아님 (요청 전) | "웹훅 주소가 올바르지 않습니다…" |
| 연결 실패(연결 10초 초과 포함). 요청은 가지 않았다 | "Slack에 연결하지 못했습니다. 인터넷 연결을 확인해 주세요: {가장 안쪽 원인}" |
| 전체 15초 초과 | "Slack 응답 시간 초과입니다. 채널에 메시지가 올라갔는지 확인한 뒤 다시 보내 주세요" |
| 연결 뒤 응답 없이 끊김 등 그 밖의 요청 오류 | "Slack 응답을 받지 못했습니다({가장 안쪽 원인}). 채널에 메시지가 올라갔는지 확인한 뒤 다시 보내 주세요" |
| 3xx, 200이 아닌 2xx, 본문이 `ok`가 아니거나 읽지 못한 200 | "Slack 응답을 확인하지 못했습니다(HTTP {상태}). 채널에 메시지가 올라갔는지 확인한 뒤 다시 보내 주세요" |
| 404, 410, 본문 `no_service`·`channel_not_found`·`channel_is_archived` | "웹훅이 없거나 삭제됐습니다(HTTP {상태}: {코드})…" |
| 403, 본문 `action_prohibited` | "Slack이 이 채널로 보내는 것을 막았습니다(…). Slack 관리자에게 확인해 주세요" |
| 429 | "Slack 전송 한도를 넘었습니다(HTTP 429)…" |
| 그 밖의 4xx·5xx (대체 경로의 400 포함) | "Slack 오류: HTTP {상태}: {코드}" |

- **자동 재시도는 없다**: 응답만 잃었을 뿐 Slack에는 이미 올라갔을 수 있어, 다시 보내면 두 번 올라간다. "다시 보내기"는 녹음자의 클릭이다. 위의 S5 대체 경로만 예외다(거부된 요청은 올라가지 않았다). 대체 경로는 400에서만 타고, 확인하지 못한 응답(3xx, 그 밖의 2xx)에서는 타지 않는다.
- **테스트 메시지** (ONB-06, `send_test_message`): 설정 Slack 탭의 펼친 웹훅 행에서 보낸다. 본문은 고정 문구 "회의 요약 테스트 메시지입니다. 이 채널로 회의록이 전송됩니다."와, 저장된 녹음자 이름이 있으면 "녹음: {이름}" 줄이고, `{"text": …}` 하나로 보낸다. `text`는 mrkdwn이라 `&` `<` `>`를 이스케이프해 이름이 멘션이 되지 않는다. 주소는 그 행에 입력하고 저장하지 않은 URL이 있으면 그것, 없으면 키체인의 URL이다. 주소 검사(`webhook_url`), 요청과 시간 제한(`post`), 실패 문구(`Failure`)는 회의 전송과 같다. 회의, `last_channel`, 키체인은 바꾸지 않는다. 입력한 URL을 Rust로 넘기므로 웹뷰가 `https://`(또는 이 PC의 `http://`) 주소로 고정 문구를 보내게 할 수 있다. 문구가 고정이라 받아들였다.
- **`send_to_slack`의 순서**: 같은 회의의 전송이 이미 돌고 있으면 바로 거부한다(회의별 잠금, 두 번 누름 방지). `no_speech`이면 거부한다(SUM-10). `save_summary`와 같은 경로로 제목·본문을 먼저 저장한다(`review`에서만). 그래서 보낸 것이 저장된 것이다. 이어서 지난 시도의 `error`를 지운다(새 시도가 시작됐으니 더는 맞지 않는 원인이다. 그사이 다시 연 회의 문서에도 보이지 않는다). 그다음 웹훅 이름 확인 → 12,000자 검사 → 수정 수(7.2) → 키체인 → 요청이다. 성공하면 `store.update`로 `sent`와 `meta.sent`를 쓰고 `error`를 지운 뒤 `last_channel`을 그 웹훅으로 바꾼다(9.1). 삭제된 회의의 늦은 결과는 다른 쓰기와 같이 버려진다(8.3). 실패하면 `review` 그대로 `error`에 원인을 쓰고 원인을 돌려준다. 보냈는데 `sent`를 쓰지 못했으면 "Slack에는 보냈지만 전송 기록을 저장하지 못했습니다"로 알린다(다시 보내면 두 번 올라간다). 회의별 잠금을 쥔 동안 `get_meeting`의 `sending`이 참이고, 끝나면(성공·실패 모두) `send_to_slack`이 `slack://finished`(회의 id)를 보낸다(10.1, 10.2).

### 7.2 수정 수 계산 (SND-03)

- `summary.generated.md`에서 제목 줄을 뺀 본문(`split_title`)과 전송본을 줄 단위 LCS로 비교한다(직접 구현, 수십 줄).
- 추가·삭제·변경된 줄 수를 N으로 한다. 변경은 삭제와 추가가 붙어 있는 경우를 1로 센다. 그래서 두 공통 줄 사이에 지운 줄 r개와 더한 줄 d개가 있으면 max(r, d)다.
- 제목이 바뀌었으면 1을 더한다. LLM 제목도 저장 규칙(`store::one_line`)으로 한 줄로 만든 뒤 비교한다. 공백만 다른 제목은 바뀐 것이 아니다.
- `summary.generated.md`가 없는 회의는 빈 요약과 비교한다(모든 줄과 비어 있지 않은 제목이 수정).
- 결과는 `meta.json`의 `sent.edit_count`에 기록하고 꼬리말 "(수정 N곳)"에 쓴다.

## 8. 저장과 상태

### 8.1 폴더 구조

- `settings.json`은 앱 데이터 폴더(Tauri `app_data_dir`, Windows는 `%APPDATA%`)에 둔다.
- 용량이 큰 `models/`와 `meetings/`는 **로컬 앱 데이터 폴더**(Tauri `app_local_data_dir`, Windows는 `%LOCALAPPDATA%`)에 둔다. Windows Roaming 프로필 동기화에 녹음 파일과 GB 단위 모델이 섞이지 않게 하려는 것이다(M1 코드 리뷰). macOS는 두 경로가 같다.

```
{앱 데이터}/
  settings.json            비밀값 없는 설정
{로컬 앱 데이터}/
  models/                  5.1의 모델 파일 (받는 중에는 {파일}.part)
  meetings/
    2026-10-13T1400-a1b2/
      meta.json
      mic.wav
      system.wav
      chunks.json              구간 계획 (5.2)
      transcript.partial.jsonl 끝난 구간 결과 (5.2)
      transcript.json          전사본 (5.2)
      worker.log               워커 stderr (5.3)
      summary.generated.md
      summary.md
```

### 8.2 meta.json

```json
{
  "schema_version": 1,
  "id": "2026-10-13T1400-a1b2",
  "title": "주간 개발 회의",
  "status": "review",
  "created_at": "2026-10-13T05:00:03Z",
  "duration_ms": 3512000,
  "gaps": [{ "at_ms": 1200000, "len_ms": 45000, "reason": "sleep" }],
  "backend": "gpu",
  "chunks_done": 6,
  "llm_connection": "회사 클라우드",
  "summarize_local": false,
  "no_speech": false,
  "error": null,
  "sent": { "channel": "#회의록", "at": "...", "edit_count": 3 }
}
```

- 시각은 UTC로 저장한다(`created_at`, id의 시각 부분). 화면에는 로컬 시각으로 보여 준다.
- `title`은 요약이 끝나면 LLM이 쓴 제목(6.2)이고, 회의 문서에서 고칠 수 있다(`save_summary`). `llm_connection`·`summarize_local`은 6.1, `no_speech`는 6.5다. `no_speech`는 M4에서 더했고 없으면 `false`로 읽는다(스키마 버전은 그대로 1).
- 회의 문서에서 고친 요약 본문은 `summary.md`에 쓴다. `summary.generated.md`는 LLM이 쓴 그대로 두고 M5의 수정 수 계산(7.2)이 비교한다.
- `sent`(M5)는 보낸 회의에만 있다: `channel`은 웹훅 이름(설정의 `webhooks[].name`, 예: "#회의록"), `at`은 보낸 시각(UTC, `created_at`과 같은 형식), `edit_count`는 7.2의 N이다. `review`의 `error`는 마지막 전송 실패의 원인이다(큐는 요약을 시작할 때 `error`를 지우므로 `review`에서는 전송만 쓴다). 다음 전송이 성공하면 지운다.
- 쓰기는 항상 임시 파일에 쓴 뒤 이름 바꾸기로 한다. 쓰는 도중 크래시가 나도 파일이 깨지지 않는다.
- **단일 쓰기 경로**: 기록 스레드, 처리 대기열, UI 명령이 모두 `meta.json`을 고친다. 그래서 모든 변경은 `store.rs`의 회의별 잠금(`Mutex`) 안에서 읽고-고치고-쓴다. 원자적 이름 바꾸기는 파일 손상을 막을 뿐, 서로의 변경을 덮어쓰는 것은 막지 못하기 때문이다.
- **스키마 버전** (STO-05, eng review D9): `meta.json`과 `settings.json`에 `schema_version`을 둔다. 앱이 아는 버전보다 높으면 그 데이터를 읽기 전용으로 열고 "새 버전 앱에서 만든 데이터입니다"를 보여준다. 낮으면 읽을 때 현재 버전으로 옮긴다.

### 8.3 상태 전이

```
recording ─▶ recorded ─▶ transcribing ─▶ transcribed ─▶ summarizing ─▶ review ─┬▶ sent
                              │  ▲                           │  ▲              └▶ archived
                              ▼  │                           ▼  │
                            paused / transcribe_failed     paused / summarize_failed
(어느 상태에서든) ─▶ 삭제
```

- 앱이 모르는 상태값이나 더 높은 `schema_version`의 `meta.json`은 `unknown` 상태의 읽기 전용 회의로 보여 준다(목록에서 사라지지 않게). 폴더 이름이 회의 id의 기준이다(`meta.json` 안의 `id`를 믿지 않는다).
- 실패 상태는 `transcribe_failed`와 `summarize_failed` 두 가지다. 설계 문서의 "각 단계에는 실패 상태가 있다"를 이렇게 구체화했다.
  - 녹음 단계의 문제(장치 끊김, 절전)는 실패가 아니라 `recorded`로 넘어간다.
  - 전송 실패는 상태가 아니라 `review`에 붙은 `error`로 기록한다. 다시 보낼 수 있어야 하기 때문이다.
- `transcribe_failed`, `summarize_failed`에서는 각각 `resume_meeting`, `retry_summary`(10.2)로 다시 시도한다.
- **삭제 절차** (REV-04, eng review outside voice #4):
  1. `meta.json` 상태를 `deleting`으로 기록한다.
  2. 진행 중인 작업을 취소한다. 녹음 중이면 녹음을 끝내 파일을 닫고, 워커가 돌고 있으면 kill하고, LLM 요청이 진행 중이면 취소한다.
  3. 그 작업들이 실제로 멈출 때까지 기다린다.
  4. 회의 폴더를 지운다. 폴더 안의 다른 파일을 먼저 지우고 `meta.json`을 마지막에 지운다. 중간에 실패해도 `deleting` 상태의 `meta.json`이 남아 다음 실행 때 복구가 삭제를 마저 한다(M1 코드 리뷰).
  - 대기열과 `store.rs`는 `deleting`이거나 이미 없는 회의에 대한 늦은 결과(워커 출력, LLM 응답, 기록 스레드 flush)를 모두 버린다. 쓰기 전에 회의 존재와 상태를 잠금 안에서 확인한다.
  - 앱이 4단계 전에 꺼지면, 다음 실행 때 복구 단계가 `deleting` 회의의 폴더를 마저 지운다.

### 8.4 처리 대기열과 시작 시 복구 (queue.rs, store.rs, lib.rs)

- 대기열에서 회의를 들어온 순서대로 꺼내 2개까지 동시에 처리한다(5.3). 처리가 끝나면(녹음으로 멈춘 경우와 모델이 사라진 경우 말고는) 대기열에서도 뺀다.
- **한 자리에서 전사 → 요약** (M4): 회의 하나의 처리 스레드가 전사를 마치고 대기열로 돌아가지 않고 바로 요약한다. 그래서 동시에 도는 회의는 전사·요약을 합쳐 2개다. 무엇을 할지는 상태로 정한다: `transcribed`, `summarizing`(멈춤을 쓰지 못한 경우), `summarize_failed`(다시 실행), 그리고 `transcript.json`이 있는 `paused`(요약하다 멈춤)는 요약만 한다. 그 밖에는 전사부터 한다. 파일만 보고 정하지 않는 이유는, `transcript.json`을 쓴 뒤 상태를 쓰지 못한(디스크가 가득 찬) `transcribe_failed` 회의가 영영 요약도 전사도 못 하게 되기 때문이다. 이런 회의는 다시 전사하는데, 끝난 구간은 `transcript.partial.jsonl`에서 이어받으므로 워커를 다시 띄우지 않는다.
  - LLM 연결이 하나도 없으면 전사를 마친 회의는 실패가 아니라 `transcribed`에서 멈춘다. 연결을 저장하면(`save_settings`가 아래의 "대기열에 넣기"를 다시 한다) 요약 대기열에 들어간다.
  - 모델 파일이 없는 동안은 요약만 남은 회의도 시작하지 않는다(대기열은 앞에서부터만 꺼낸다). 받지 않은 모델로 바꾼 경우에만 생기는 일이라 그대로 둔다.
- 녹음이 시작되면 실행 중인 전사 워커를 모두 kill하고(5.3), 로컬 LLM 요약이면 요청도 취소한다(SUM-09). 녹음이 끝나면 같은 회의의 같은 구간부터 다시 진행한다. 요약을 취소한 회의는 `transcript.json`이 있으므로 다시 전사하지 않고 요약부터 다시 한다.
  - 클라우드 요약은 녹음 중에도 계속 돌고 대기열 자리도 지킨다. 녹음 중에 끝나면 `review`가 된다. 끝나서 빈 자리에는 녹음이 끝날 때까지 아무것도 시작하지 않는다.
  - 녹음 중에는 아무 회의도 시작하지 않는다. 멈춘 회의는 `paused`로 기록하고 대기열 맨 앞으로 돌아간다. 녹음으로 멈춘 실행이 끝을 쓰기 전에 삭제나 종료가 왔으면 맨 앞으로 돌려놓지 않는다(없는 회의가 대기열에 남지 않게).
  - 녹음 시작은 `Recorder::start`가, 녹음 끝은 기록 스레드가 알린다. 그래서 4시간·절전·디스크 부족으로 스스로 끝난 녹음도 대기열에 들어간다. 녹음 시작이 실패하면 대기열을 바로 다시 돌린다. 앞 녹음의 기록 스레드가 아직 파일을 닫는 중이면 새 녹음은 그 스레드가 끝날 때까지 기다린다. 앞 녹음의 "녹음 끝" 알림이 새 녹음의 "녹음 시작" 뒤에 와서 녹음 중에 전사가 다시 도는 일을 막는다.
  - 멈춘 회의의 `paused`를 쓰지 못했으면(디스크 오류) 디스크에는 `transcribing`이 남는다. 대기열은 이 회의를 다시 시작할 때 `transcribing`도 받아 준다(이 프로세스에서 한 회의는 한 번에 하나만 돈다). 앱을 껐다 켜면 복구가 `paused`로 고친다.
- **대기열에 들어가는 때** (TRN-01): 앱 시작(복구 뒤), 녹음이 끝날 때, 설정 저장, `resume_meeting`(중단된 녹음의 "처리 계속", `transcribe_failed` 재시도), `retry_summary`(`summarize_failed` 다시 실행). 앞의 세 경우는 `recorded`·`paused` 회의를 모두 오래된 순서로 넣고, LLM 연결이 있으면 `transcribed` 회의도 넣는다. 이미 줄에 있거나 실행 중인 회의는 다시 넣지 않는다.
- 모델 파일이 없으면 아무 회의도 시작하지 않고 기다린다(5.1). 받기·가져오기가 끝나면 시작한다.
- 삭제는 `deleting`을 먼저 쓰고, 대기열에서 빼고, 워커를 kill하고, 그 회의의 처리가 끝날 때까지 기다린 뒤 폴더를 지운다(8.3 2~3단계). 같은 회의를 두 번 지우면 두 번째도 처리가 끝나기를 기다린다. 먼저 끝난 쪽이 폴더를 지웠으면 두 번째는 그대로 성공한다.
- 처리 스레드가 패닉해도(디버그 빌드) 실패로 기록하고 자리를 비운다. 릴리스 빌드는 `panic = "abort"`라 앱이 끝나고, 다음 실행 때 복구가 처리한다.
- **단일 실행** (APP-06, eng review D14): `tauri-plugin-single-instance`를 빌더에 가장 먼저 등록한다. 두 번째 실행은 즉시 끝나고, 실행 중인 인스턴스가 메인 창을 보여 주고 앞으로 가져온다. 그래서 아래 복구는 항상 회의 폴더를 소유한 인스턴스 하나에서만 돈다.
- 앱 시작 시 `store.rs`의 복구 함수가 모든 `meta.json`을 읽어 다음을 한다.
  - `recording` → 디스크의 상태는 그대로 두고, 메모리에서 "중단된 녹음"으로 표시한다. 녹음자가 "처리 계속"을 고르면 `recorded`로 바꿔 대기열에 넣는다. 종료 확인(8.5)의 "진행 중인 작업"에는 세지 않는다. 실행 중에 녹음을 끝냈는데 `recorded`를 쓰지 못한 회의(디스크가 가득 참 등)도 "중단된 녹음"이 된다. 공간을 비운 뒤 "처리 계속"이 다시 쓴다.
  - `deleting` → 폴더 삭제를 마저 한다.
  - `transcribing`, `summarizing` → 앱 자체가 중간에 꺼진 경우다(워커 크래시와 무관). 디스크에 `paused`로 고쳐 쓴 뒤 대기열에 넣는다. 실제로 돌지 않는 작업을 디스크가 "진행 중"이라고 주장하지 않게 하려는 것이다.
  - `paused`, `recorded`, `transcribed` → 대기열에 넣는다. `transcribed`는 LLM 연결이 있을 때만 넣는다.

### 8.5 앱 종료 처리 (APP-02, TRN-06)

Tauri 2는 종료 경로에 따라 보내는 이벤트가 다르다(tauri #9198, #14558).

| 종료 경로 | 이벤트 | 처리 |
|---|---|---|
| 트레이 메뉴 "종료", 직접 만든 앱 메뉴 "종료"(`CmdOrCtrl+Q` 단축키, `app.exit(0)` 호출) | `ExitRequested` → `Exit` | 진행 중인 녹음·처리가 있으면 `prevent_exit()` 후 확인을 받는다. 확인하면 `paused`를 기록하고 종료한다 |
| macOS Dock "종료", OS 종료·로그아웃 | `Exit`만 | 확인을 받을 수 없다. `Exit` 안에서 먼저 전사 워커를 모두 kill하고(자식 프로세스는 앱이 끝나도 남는다) 요약 요청을 취소한다. 녹음 중이면 녹음을 끝내 두 WAV를 닫고 `recorded`를 쓴다(기록 스레드 한 주기, 수십 ms). 그다음 진행 중인 회의의 `meta.json`을 동기로 `paused`로 기록한다. 빠르게 끝나야 하므로 회의마다 파일 하나 쓰기만 한다 |
| 크래시, 강제 종료, 전원 차단 | 없음 | 다음 실행 때 8.4 복구와 5.4 비정상 종료 판정이 처리한다. 녹음은 5초 flush 덕분에 최대 5초만 잃는다 |

- macOS 기본 앱 메뉴의 "Quit" 항목은 `ExitRequested`를 보내지 않으므로, 기본 메뉴 대신 직접 만든 메뉴를 쓴다.
- 직접 만든 앱 메뉴(종료 `CmdOrCtrl+Q` + "편집" 하위 메뉴)는 **macOS에만** 둔다. 편집 메뉴가 없으면 macOS 입력란에서 복사·붙여넣기 단축키가 동작하지 않는다.
- Windows는 메뉴 막대를 두지 않는다. 대신 프론트엔드가 Ctrl+Q를 받아 `request_quit` 명령을 부르고, 이 명령이 `app.exit(0)`을 호출해 같은 `ExitRequested` 경로를 탄다.
- 종료 확인 뒤 다시 `ExitRequested`가 와도 막지 않도록 "종료 확정" 플래그를 둔다. 상태를 고칠 수 없는 회의(새 버전 스키마, 디스크 오류)가 있어도 종료가 무한 반복되지 않게 하려는 것이다(M1 코드 리뷰 P1).

### 9.2 키체인

- 서비스 이름: `com.sije.meeting-summarizer`
- 비밀값 존재 확인(`has_secret`)은 값을 복호화하지 않는다. macOS에서는 `keyring-core`의 속성 전용 검색을 써서 키체인 접근 팝업을 피한다(`keyring-core`는 `keyring`과 같은 버전을 유지해야 한다).
- 키체인에 주인 없는 항목이 남지 않게 한다. 키체인은 "저장"으로만 바뀌고, `settings.json` 저장(`save_settings`)이 성공한 뒤에 다음 순서로 바뀐다. 저장이 실패하면 키체인은 그대로다.
  1. 지운 연결·웹훅의 항목을 지운다. 지울 때는 확인을 받는다.
  2. 입력한 키를 넣는다. 같은 저장에서 새로 추가한 연결·웹훅도 이미 `settings.json`에 들어 있으므로 바로 넣는다.
- 키 쓰기나 지우기가 실패하면 "설정은 저장했지만 키체인에 키를 저장하지 못했습니다"(지우기는 "…지우지 못했습니다")를 보여 준다. 실패가 여럿이면 한 메시지에 모은다. 입력한 키는 화면에 남아 다음 저장 때 다시 넣고, 지우지 못한 키는 기억해 두었다가 다음 저장 때 다시 지운다. 그동안 그 이름은 다시 추가할 수 없다. 이 기억은 설정 화면에만 있어서, 지우기가 실패한 채 앱을 다시 시작하면 그 키는 키체인에 남는다.
- 저장하는 동안에는 설정 화면의 입력과 저장 버튼을 막아 두 저장이 겹치지 않게 한다.
- 저장한 연결·웹훅을 지운 뒤 같은 이름을 저장 전에 다시 추가할 수 없다("저장한 뒤 다시 추가하세요"). 옛 키가 1번에서 지워지지 않고 새 항목에 남기 때문이다.
- 계정 이름: `llm:{연결 이름}`, `slack:{웹훅 이름}`
- 값: API 키, 웹훅 URL
- 비밀값을 읽는 것(`settings::get_secret`)은 Rust 안에서 요청을 보내기 직전뿐이다(LLM 요약은 6.1, Slack 전송과 테스트 메시지는 7.1). 명령으로 열지 않고, 웹뷰로 돌려주지 않고, 로그에 쓰지 않는다. 대기열과 Slack 전송의 테스트는 이 읽기를 가짜로 바꿔 실제 키체인을 건드리지 않는다.

### 9.3 연결 설정 입력 (ONB-04)

- 녹음자가 설정 화면의 요약(LLM) 탭과 Slack 탭에서 직접 입력한다: LLM 연결(`name`, `base_url`, `model`, API 키)과 Slack 웹훅(이름, URL).
- 로컬 연결의 컨텍스트 토큰은 모델의 최대 길이가 아니라 **서버에 설정한 컨텍스트 길이**를 넣는다(Ollama `OLLAMA_CONTEXT_LENGTH`, LM Studio 모델 로드 시 Context Length). 더 크게 넣으면 서버가 입력을 말없이 잘라 요약이 실패한다(6.1 입력 잘림 감지).
- 설정 화면의 "저장" 버튼 하나가 모든 탭을 저장한다. API 키와 웹훅 URL은 키체인에, 나머지는 `settings.json`에 들어간다(순서는 9.2). 입력한 키는 저장 전까지 화면 상태에만 있고, 저장한 키는 프론트엔드로 돌아오지 않는다. 입력란은 "키체인에 저장됨"만 보여 주며, 새 값을 입력하고 저장하면 바뀐다. 저장하지 않고 설정 화면을 떠나면 입력한 값(키 포함)은 버려진다.
- 설정 파일 가져오기는 v1에서 뺐다(eng review D3). 평문 비밀값 파일을 만들지 않기 위해서다. 키와 URL을 녹음자에게 어떻게 전달할지는 설계 문서 Open Question 3이다.

온보딩 화면은 없다(사용자 결정 2026-10-14, ONB 절). 회의가 하나도 없을 때의 홈이 첫 화면이다(디자인 시스템 6.5): 투어·체크리스트·설정 강요 없이 녹음 버튼, 네 단계 한 줄, 설정 줄만 있다.

- **앱 헤더** (APP-07): 모든 화면 위에 붙는 높이 48px 헤더 하나(디자인 시스템 6.1). 왼쪽은 회사 로고(SIJE)와 가는 구분선, 워드마크 "회의 요약"(Pretendard)이고, 오른쪽은 설정 버튼이다. 상태 칩은 없고 녹음·처리 상태는 독이 보인다.
  - 독, 홈 목록, 회의 문서는 `App.tsx`가 들고 있는 `list_meetings` 결과와 회의별 마지막 `meeting://progress`로 같은 판정(`common.tsx`의 `phase`)을 써서 어긋나지 않는다. 마지막 이벤트가 실행 중(`transcribing`·`summarizing`)이라고 하면 목록의 상태와 상관없이 실행 중으로 본다: 전사가 끝나고 요약이 시작되기 전에 목록이 `transcribed`를 읽어도 독이 그 회의를 놓았다 다시 잡으며 깜빡이지 않게 하려는 것이다.
  - 목록은 화면이 바뀔 때, `recording://stopped` 때, 진행률 이벤트의 `status`가 바뀔 때, 전송이 끝날 때(`slack://finished`), 녹음을 끝냈을 때 다시 읽는다. 늦게 온 옛 응답은 버린다. 진행률은 이벤트를 먼저 듣고 그다음 `queue_state`로 채운다. 둘이 겹치면 이벤트가 이긴다. 폴링은 하지 않는다.
- **독** (`components/Dock.tsx`, 디자인 시스템 6.2): 화면 아래 가운데 고정된 먹색 알약. 상태는 셋이다.
  - 녹음 중: 숨 쉬는 빨간 점, 미니 파형 12막대, 경과 시간(mm:ss, 자리마다 굴러 바뀐다), "종료 ⌘.". 앞부분(이름 "녹음 중 12:34")을 누르면 녹음 화면, 종료 버튼(이름 "녹음 종료")은 녹음을 끝내고 지금 화면에 머문다. 파형은 `recording://level`마다 막대의 `style.transform`에 바로 쓰고(React 상태 없음), 경과 시간만 초 단위 상태다. 첫 값은 회의의 `created_at`에서 채운다. 종료를 누른 뒤 목록이 바뀔 때까지는 "전사를 시작합니다"다.
  - 처리 중(녹음 중이 아닐 때): 원형 진행 표시, "처리 중 N", 줄 맨 앞 회의 한 줄("주간 회의 · 전사 42%", "14:00 회의 · 요약 2/3", "… · 대기 중"). N은 처리 중 + 대기다. 처리 중은 `transcribing`·`summarizing`, 대기는 `recorded`·`paused`이거나 대기 순서가 있는 회의다(다시 시도한 `transcribe_failed`·`summarize_failed`, 요약을 기다리는 `transcribed` 포함). 대기 순서가 없는 `transcribed`는 LLM 연결이 없어 멈춘 회의라 세지 않는다(APP-07). 줄 맨 앞은 처리 중 회의(목록 순서), 없으면 대기 순서 1번이다. 퍼센트는 구간 계획이 나온 전사에만, 요청 수는 LLM 요청이 둘 이상인 요약에만 붙인다. 끝난 회의의 마지막 이벤트는 목록을 다시 읽기 전이라도 진행을 붙이지 않는다. 원과 퍼센트 글자는 스프링 MotionValue 하나로 그려 리렌더하지 않는다. 누르면 그 회의의 문서다. 녹음이 처리를 멈추므로(TRN-09) 녹음 중에는 처리 독을 보이지 않는다.
  - 없음: 아래로 사라진다. 녹음 화면에서도 숨는다(그 화면이 다 보인다).
  - 모양 변화는 `layout` + 안쪽 `AnimatePresence mode="popLayout"`, 모서리는 `style`의 `borderRadius`, 고정 컨테이너는 `layoutRoot`다. 상태가 바뀌면 숨은 `role="status"` 한 줄이 한 번 말한다("녹음을 시작했습니다", "녹음을 마쳤습니다. 처리를 시작합니다", "처리를 시작했습니다", "처리를 마쳤습니다"). 독은 첫 목록을 읽은 뒤 붙어 앱을 연 순간의 상태는 말하지 않는다. 버튼 높이 40px, 포커스 링은 흰색(먹색 위 brand 링은 3.2:1).
- **단축키**: `⌘R` 녹음 시작, `⌘.` 녹음 종료(Windows는 `Ctrl+R`, `Ctrl+.`). `App.tsx`가 창의 `keydown`을 듣는다. 창에 포커스가 있을 때만 오고, 입력란·`select`·`contenteditable` 안이거나 대화상자(`role="dialog"`/`"alertdialog"`)나 열린 선택 목록·메뉴(`listbox`/`menu`)가 있으면 무시하며, 키 반복도 무시한다. 녹음 중이거나 시작 중이면 `⌘R`을, 녹음 중이 아니거나 끝내는 중이면 `⌘.`를 무시한다. 무시할 때도 `preventDefault`는 해 웹뷰가 새로 고쳐지지 않는다. 키는 `e.code`(`KeyR`, `Period`)로 본다(한글 입력 중에도 같다). 단축키로 생긴 화면 전환은 움직이지 않는다. 버튼은 `aria-keyshortcuts`를 갖고 `⌘R` 표시는 화면용(`aria-hidden`)이다. macOS 앱 메뉴(8.5)에는 겹치는 항목이 없다. Windows WebView2가 자체 `Ctrl+R` 새로 고침을 페이지의 `preventDefault`보다 먼저 처리하는지는 확인하지 않았다(Windows 미검증).

Enter는 줄을 바꾸지 않고 붙여 넣은 줄바꿈은 공백이 되며 캐럿은 제자리에 남는다. 포커스 때 2px 브랜드 선이 왼쪽에서 펼쳐진다), 그 밖에는 글자다. 제목이 아직 없으면 `ink-2`로 "제목은 요약 뒤에 붙어요"(요약이 있는데 비었으면 "제목 없음").
  - **요약 전** (대기·전사 중·요약 중, 실패, LLM 연결이 없어 멈춤): 단계 줄 "녹음 ✓ › 전사 42% › 요약 › 검토"(사이는 `ChevronRight`, `aria-hidden`)(`ol` "처리 단계", 지금 단계는 `aria-current="step"`, 지난 단계는 화면 읽기용 "완료"). 지금 단계에는 전사 세 막대·대기 점·실패 아이콘이 붙고, 구간 계획이 나온 전사는 퍼센트를 스프링 MotionValue로 그린다(리렌더 없음, 움직임 줄이기면 `jump`). 그 아래 한 줄은 "구간 2/5 · 약 3분 남음", "구간 나누는 중", "대기 중 · 2번째"와, `backend`가 있으면 "처리 장치 GPU"다. 보일 값이 있는 진행(구간 계획 뒤 전사, 구간 나누기, 요청이 둘 이상인 요약)은 숨은 `role="progressbar"`(이름 "전사 진행률"·"구간 나누기 진행률"·"요약 진행률")가 값을 알린다. 지금 단계는 실행 중 이벤트(`transcribing`·`summarizing`)가 있으면 그 이벤트의 단계이고(`phase`처럼 이벤트가 목록보다 앞선다. 전사가 막 끝나 `transcribed`로 읽혀도 마지막 이벤트가 전사면 전사다), 없으면 `transcribed`·`summarizing`·`summarize_failed`, 요약하다 멈춘 `paused`(연결이 정해져 있다)이면 요약이고 그 밖은 전사다. 요약의 첫 이벤트는 `chunks`가 0이지만 구간 나누기가 아니므로 `status`로 가른다. "구간" 문구는 `status`가 `transcribing`일 때만 쓰고, 다시 읽기 전에 온 마지막 이벤트(`review`, `summarize_failed` 등)는 진행을 그리지 않는다.
    - 그 아래 요약 경로 안내(`RouteNotice`, SUM-07·08): 요약이 시작되기 전(`summary_route`의 `locked`가 아닌 동안)에는 녹음 화면과 같은 안내와 "로컬로 요약" 토글, 잠긴 뒤에는 토글 없이 `summarizing`인 동안만 "전사본을 {이름}({호스트})(으)로 보내 요약하고 있습니다"(로컬이면 "이 PC의 {이름}(으)로 요약하고 있습니다")다. 끝나면 메타 줄이 맡는다. 상태가 바뀌면 다시 읽고, 읽기와 토글의 응답은 한 요청 번호를 같이 써서 가장 새 응답만 반영한다.
    - 대기·처리 중이면 그 아래 다섯 섹션 모양의 옅은 뼈대(`aria-hidden`)다. 요약 중이면 "요약을 쓰고 있어요"(LLM 요청이 둘 이상이면 " · 2/3")와 막대마다 지나가는 반짝임(`motion-safe:`)이다.
    - 실패(대기 순서가 없는 `transcribe_failed`·`summarize_failed`): 오류 배너와 "다시 시도"(`resume_meeting`), 또는 연결 고르기와 "요약 다시 실행"(SUM-06). 연결은 `get_settings`의 LLM 연결에서 고른다. 기본값은 회의의 `llm_connection`(아직 있으면), 없으면 기본 LLM, 그것도 없으면 첫 연결이다. 선택지는 "{이름} (이 PC)" 또는 "{이름} ({호스트}로 전송)"이라 어디로 보낼지 고르면서 안다(SUM-07). 고른 이름으로 `retry_summary`를 부른다. 키가 없거나 거부된 실패(6.4)는 설정에서 고치므로 요약 실패에는 요약(LLM) 탭으로 가는 버튼을 늘 함께 둔다. 연결이 하나도 없으면 "LLM 연결을 추가하면 요약을 다시 실행할 수 있습니다"를 더한다. 다시 줄에 서면 그 이벤트가 오류와 버튼을 거둔다.
    - 대기 순서가 없는 `transcribed`(LLM 연결이 없어 멈춤)는 "LLM 연결을 추가하면 요약합니다"와 요약(LLM) 탭으로 가는 버튼이다. 마지막 `transcribing` 이벤트가 남아 있는 동안(전사가 막 끝나고 요약이 시작되기 전)은 `phase`가 처리 중으로 보므로 보이지 않는다.
  - **문서 보기** (요약이 있는 모든 상태): 요약 본문은 Markdown 원문이 아니라 읽는 문서로 그린다. Markdown 라이브러리 없이 우리 줄 파서(`MeetingParts.tsx`의 `parseDoc`)가 프롬프트 형식(6.2)의 몇 가지 모양만 알아보고, React 요소와 글자 노드로만 그린다(10.4).
    - `# `·`## `·`### ` 줄은 섹션 제목이다(Pretendard `title`, `h2`, 위에 여백, `#`는 뺀다). `- `·`* `·`• ` 줄은 목록 항목이고(작고 조용한 점, 둘째 줄부터 글머리에 맞춘 들여쓰기), 이어진 항목은 섹션마다 `ul` 하나다.
    - 항목 앞의 `[이름]`은 담당자 칩(`sunken` 알약, `label` 크기, `ink` 글자)이고 `[미정]`이면 `marker` 바탕이다. 링크의 `[글](주소)`는 담당자가 아니다. 항목 끝의 `(…)`는 기한(`caption`, `ink-2`)이고 `(미정)`이면 `marker` 바탕에 `ink` 글자다. 그 밖의 "미정"은 형광펜(`<mark>`)이다. `- 없음`은 조용한 `ink-2` "없음"이다.
    - 나머지 줄은 문단, 빈 줄은 간격이다. 굵게·링크·HTML 같은 다른 Markdown은 쓴 글자 그대로 보인다.
    - `sent`·`archived`·새 버전 앱의 회의는 이 문서를 읽기 전용으로 보인다("고치기"도, 누르면 열리는 편집기도 없다).
  - **요약이 도착할 때**: 열어 둔 동안 요약 전 상태에서 `review`가 되면 뼈대 자리에 문서 보기가 섹션 단위로 한 번 들어온다(불투명도 + 4px, 40ms 간격, 앞 8개까지만 기다린다). 들어오는 동안은 읽기 전용이고, 끝나면 같은 문서가 고칠 수 있는 상태가 된다(원문 편집기가 아니다). 움직임 줄이기면 바로 고칠 수 있다. 한 글자씩 쓰는 연출과 모달 "생성 중"은 두지 않는다.
  - **고치기** (`review`, 현재 스키마, `no_speech` 아님): 기본은 문서 보기다. 마우스를 올리면 본문에 옅은 `sunken` 바탕이 깔린다(바깥 8px은 링이라 글자 자리는 그대로). 본문 오른쪽 위 "고치기"는 키보드와 화면 읽기 프로그램을 위해 늘 있고 평소에는 `ink-2`로 조용하다.
    - 줄을 누르면(글을 고르는 중이 아니면) 그 줄의 원문 첫 자리에 캐럿을 두고 편집기가 같은 자리에 들어선다. 블록마다 원문의 줄 번호(`data-line`)를 갖고, 누른 줄은 화면에서 같은 높이에 남도록 페이지를 맞춘다. "고치기"는 캐럿을 맨 앞에 둔다.
    - Esc나 편집기 밖으로 나간 포커스는 문서로 돌아온다. 보내기 막대를 누를 때(보내기가 실패하면 고치던 곳으로 돌아오게)와 창이 다른 앱으로 갈 때(포커스가 그대로 편집기에 있다)는 남는다. Esc로 돌아오면 캐럿이 있던 줄이 같은 높이에 남고 포커스는 "고치기"로 간다. 한글 조합 중의 Esc는 조합의 것이다.
    - 둘은 150ms 불투명도로 엇갈려 바뀌고(`swapVariants`, 떠나는 쪽은 `popLayout`으로 흐름에서 빠진다), 키보드로 바꾸면(Esc, Tab, Enter·Space로 누른 "고치기") 바로 바뀐다. 요약이 들어오는 동안과 보내는 동안에는 열 수 없다(이미 열린 편집기는 보내는 동안 읽기 전용이다).
    - 자동 저장, 떠날 때의 저장, 실패한 입력의 복원은 편집기가 열려 있든 아니든 같은 글에 대해 그대로다. 보내기는 원문 그대로의 본문을 보낸다.
  - **편집기**: 제목과 본문을 일반 텍스트로 고친다(10.4). 본문은 자동 높이 `textarea`(`body-doc`)이고 안쪽 스크롤 없이 페이지가 스크롤된다. WebKit에는 `field-sizing`이 없어서, 같은 글자를 담은 거울 층이 흐름 안에서 높이를 잡고 textarea는 그 위에 투명 바탕으로 겹친다(`MeetingParts.tsx`의 `Grow`, 제목도 같다). 마지막 빈 줄은 너비 없는 공백으로 상자를 잡는다. 포커스 표시는 왼쪽 여백의 2px 브랜드 선이다.
    - 페이지가 스크롤되므로 브라우저는 캐럿을 창 아래 끝까지만 데려오고, 그 자리는 보내기 막대와 독 아래다. 캐럿이 움직일 때마다(`select` 이벤트, 새 배치가 끝난 다음 프레임) 거울 층에서 캐럿 자리를 재어(`caretRect`) 아래 스택 위 16px까지 올린다. 위로 갈 때도 같아서, 창 맨 위(48px 머리 아래)에 멈춘 캐럿을 머리 아래 16px까지 내린다.
    - **"미정" 형광펜** (REV-01): 거울 층에 그린다. React 글자 노드와 `<mark>`(`marker` 바탕, 굵기 그대로, 테두리는 레이아웃을 바꾸지 않는 그림자)만 쓰고 `aria-hidden`이다. 거울과 textarea는 글꼴·크기·줄 높이·자간·여백·폭·`white-space: pre-wrap`·`word-break`·`overflow-wrap`·`tab-size`를 한 클래스로 맞춰 같은 자리에서 줄을 바꾸고, 폭이 같은 상자라 창 크기가 바뀌어도 어긋나지 않는다. 캐럿과 선택은 textarea의 것이다. 세리프의 높은 글자가 마지막 줄 밖으로 1~2px 나가도 넘치지 않게 둘 다 아래에 4px 여백을 둔다. 그래도 웹뷰가 캐럿을 따라 스스로 스크롤하면 0으로 되돌린다.
  - 아래 "확인할 항목 N개"(`<details>`, 처음엔 접혀 있다, 요약 높이 24px 이상): "미정"이 든 줄을 일반 텍스트로 나열한다. 형광펜은 그림뿐이라 화면 읽기 프로그램은 이 목록으로 안다. 입력할 때마다 바뀌므로 live region이 아니다.
  - 자동 저장: 마지막 입력 800ms 뒤 `save_summary`를 부르고 "저장 중…" / "저장됨"을 보인다. 저장은 한 번에 하나씩 순서대로 보내 옛 본문이 새 본문을 덮지 않고, 마지막 저장의 결과만 화면에 반영한다. 실패하면 오류 배너를 보이고 입력한 글은 그대로 두며, 다음 저장 때 다시 보낸다. 화면을 떠날 때와 "전송 안 함"·".md로 저장" 전에 남은 입력을 바로 저장한다(저장이 실패하면 둘은 멈춘다). 돌아온 `meta.title`(한 줄로 고친 제목)은 그 사이 더 입력하지 않았을 때만 반영하고, 입력한 제목이 공백으로 끝났으면 공백 하나를 붙여 둔다(멈췄다 이어 치는 공백을 지우지 않게).
  - 저장 상태(아직 저장하지 못한 입력과 마지막 저장)는 회의 id별로 모듈 변수에 두어 화면보다 오래 산다(모델 받기 상태와 같은 방식). 다시 연 회의 문서는 이전 방문의 마지막 저장이 끝난 뒤에 `get_meeting`을 읽고, 저장하지 못한 입력이 남아 있으면 그것을 입력란에 되돌려 다시 저장한다. 화면을 떠난 뒤 저장이 실패하면 앱의 닫을 수 있는 경고 배너에 "회의 문서에서 고친 내용을 저장하지 못했습니다: …"를 보인다. 삭제하면 저장할 것을 버리고, 이미 나간 저장이 그 뒤 실패해도 그 입력을 되살리지 않는다(다시 보내지도, 알리지도 않는다).
  - **전사본 패널**: 위 오른쪽 "전사본"(`aria-expanded`)이 오른쪽 400px 패널(`<aside>` "전사본", `surface`, `float` 그림자)을 연다. 버튼은 `transcript.json`이 있는 동안(`transcribed`부터, 요약하다 멈춘 `paused`) 있다. 처음 열 때 `get_transcript`를 한 번 읽고, 시각(Pretendard 고정폭)과 글을 `TranscriptList`로 보인다(10.4). 우리 전사본은 두 트랙을 합친 것이라 나/상대 말풍선은 없다. "전사본 복사"는 `[mm:ss] 텍스트` 줄이다. 열면 포커스가 패널 제목으로 들어가고, 닫으면(Esc, 닫기, 버튼) "전사본" 버튼으로 돌아온다. 다른 것이 이미 받은 Esc는 패널이 받지 않는다: Radix 대화상자·메뉴·선택 목록은 닫기 전에 `preventDefault`하고(움직임 줄이기면 나가는 애니메이션이 없어 창이 Esc를 들을 때 그 요소는 이미 없다), 편집기의 Esc도 그렇다. transform으로 미끄러져 들어오고(240ms `ease.out`) 나갈 때는 그 65%다. 키보드로 열고 닫으면 움직이지 않는다. 화면이 바뀌면 함께 나간다. 화면 전환이 화면을 움직이는 동안 `fixed` 패널이 따라 움직이지 않게 `body`에 포털로 둔다.
  - **더보기(⋯)** (`DropdownMenu`, Enter·Space·↓로도 열린다): "요약 복사"(`# 제목`, 빈 줄, 본문을 클립보드에), ".md로 저장"(REV-05 `export_markdown`. 저장하면 "저장했습니다: {경로}", 취소하면 아무것도 보이지 않는다), "전송 안 함"(REV-03: 나중에 보낼 수 없다는 확인 창 뒤 `archive_meeting`, 그리고 홈으로), "삭제"(확인 창, REV-04). 요약 복사와 .md는 요약이 있을 때만, 전송 안 함은 `review`일 때만이고, 보내는 동안 전송 안 함·삭제는 막힌다. 복사 결과("복사했습니다" / "클립보드에 복사하지 못했습니다", 3초)와 저장 경로는 ⋯ 옆 작은 글자다(`role="status"` 둘이라 복사 결과가 사라질 때 경로를 다시 읽지 않는다). `writeText`는 메뉴 선택 처리 안에서 바로 부른다(WebKit은 사용자 동작 안의 클립보드 쓰기만 허용한다). 확인 창이 닫히면 포커스는 ⋯로 돌아온다.

  - **제목 공유 전환** (디자인 시스템 6.1): 홈 행 제목과 문서 제목은 같은 `layoutId`("title-{id}")다. `layoutId`는 입력란이 아니라 감싼 요소에 두고 `layout="position"`이라 글자가 늘어나지 않고 왼쪽 위 모서리 자리만 미끄러진다(300ms `ease.out`. 매일 보는 화면의 300ms 상한 때문에 `spring.gentle` 대신 tween). 홈 행은 여는 버튼(행 버튼, "검토하기"·"요약 다시 실행")에 포인터가 눌린 행과, 클릭으로 돌아온 회의의 행만 600ms(`TITLE_GLIDE_MS`) 동안 `layoutId`를 갖는다. 모든 행이 가지면 다른 묶음으로 옮겨 붙는 행의 제목만 미끄러지기 때문이다. Motion은 `layoutId`를 요소를 만들 때 한 번만 읽으므로 행 제목은 `layoutId`가 바뀔 때 새로 만든다(`key`). 돌아오는 미끄러짐은 그 행에서 온 회의(`screen.glided`)만이다: 독·알림에서 연 회의의 행은 아래쪽 보이지 않는 곳에 있을 수 있다. 이미 나가던 홈이 다시 들어오면 돌아온 회의로 600ms를 다시 센다. 문서 제목은 도착한 뒤 600ms와 나갈 때만 300ms로 움직이고, 그 밖의 자리 이동(메타 줄이 두 줄이 될 때)은 바로다. 키보드는 행을 누르지 않으므로 키보드로 연 회의는 미끄러지지 않는다. 스크롤된 페이지에서는 하지 않는다: 화면이 바뀌면 `App.tsx`가 스크롤을 맨 위로 돌리므로 제목이 행이 없는 자리에서 날아온다. 움직임 줄이기면 `MotionConfig`가 레이아웃 애니메이션을 끈다. 홈은 창이 스크롤하므로 `layoutScroll`은 필요 없다.

- **오디오 탭** (ONB-03, REC-07, REC-10): 마이크 선택, 시스템 오디오(Windows는 출력 장치 선택, macOS는 모든 출력을 녹음한다는 도움말), 묶음 아래 헤드폰 안내. 마이크 행과 시스템 오디오 행 아래에 테스트 줄이 있다(4.4): "테스트" 버튼과 한 줄의 `role="status"`가 하는 일("5초 동안 마이크 소리를 들어 봅니다"), 도는 동안 할 일("마이크에 대고 말해 보세요"), 결과를 차례로 말한다. 마이크 테스트 동안에는 버튼 옆에 가는 레벨 막대가 뜬다. 버튼 이름은 "마이크 테스트"·"시스템 오디오 테스트"이고 도는 동안 보이는 글자처럼 "… 테스트 중"이 된다. 결과는 아이콘(체크 / 원 안의 느낌표)과 `ink-2` 글자다. 실패 문구는 할 일을 말한다. macOS는 OS 설정의 목록을 번들 이름으로 가리킨다(11.1): 마이크는 "소리가 들어오지 않아요. 고른 마이크가 맞는지 보고, 시스템 설정 > 개인정보 보호 및 보안 > 마이크에서 'meeting-summarizer'를 허용하세요", 시스템 오디오는 "시스템 오디오가 잡히지 않아요. 시스템 설정 > 개인정보 보호 및 보안 > 화면 및 시스템 오디오 녹음에서 'meeting-summarizer'를 허용하세요". Windows는 "마이크 권한과 장치를 확인하세요", "고른 출력 장치로 소리가 나는지 확인하세요"다. 결과는 그 테스트가 쓴 장치의 것이라, 다른 장치를 고르면(도는 중에 골라 결과가 늦게 와도) 보이지 않는다. 녹음 중(시작 중 포함)에는 두 버튼이 쉬고, 묶음 아래 `role="status"` 한 줄이 "녹음 중에는 테스트할 수 없어요"를 한 번만 말한다.
- **일반 탭**: 녹음자 이름(행 도움말 "Slack 메시지에 표시됩니다")과, 묶음 아래 알림 권한 안내 한 줄 "알림이 보이지 않으면 OS 알림 설정에서 'meeting-summarizer'를 허용해 주세요"(ONB-03). OS 설정은 앱을 번들 이름(`productName`)으로 보이므로 화면 이름 "회의 요약"이 아니라 그 이름을 쓴다(11.1). 데스크톱 알림 권한 API는 항상 허용으로 답해 거부를 알 수 없다.
- **설정 탭** (디자인 시스템 6.7): 왼쪽 탭 목록(넓은 창에서는 `sticky`, 좁은 창에서는 내용 위)과 오른쪽 내용. 탭은 일반, 오디오, 전사, 요약(LLM), Slack이다(ONB-07). 선택한 탭은 `aria-current="page"`이고 선택 표시(`sunken`)가 `layoutId`로 탭 사이를 미끄러진다(키보드로 고르면 바로). 탭마다 제목과 한 줄 설명, 그리고 `surface` 묶음의 행(왼쪽 레이블·도움말, 오른쪽 조작)이다. 행의 `<label for>`가 조작의 이름, 도움말이 `aria-describedby`다. 안 보이는 탭도 마운트된 채 숨겨 두므로 탭을 바꿔도 입력이 사라지지 않는다. 비밀값 규칙은 9.2~9.3 그대로다.
  - **저장 막대**: 저장 버튼 하나가 모든 탭을 저장한다. 바뀐 것이 있을 때만 `App.tsx`의 아래 스택(보내기 막대와 같은 포털 자리, 독 위)에 흰 알약 "저장 안 한 변경 N개 · 되돌리기 · 저장"으로 뜬다. N은 바뀐 필드 하나씩, 추가·삭제·수정한 연결·웹훅 하나씩, 입력한 키 하나씩, 키체인에서 아직 지우지 못한 키 하나씩이다. 용어집은 저장할 모양으로 비교하고, 저장 때 고쳐 넣는 값은 세지 않는다. 저장하는 동안에는 누를 때의 N을 그대로 보이며 남는다(`settings.json`을 쓴 뒤 키체인 단계 동안 초안은 이미 저장본과 같다). 성공하면 같은 알약이 "저장했습니다"로 1.5초 남았다 내려가고 숨은 `role="status"`가 "설정을 저장했습니다"를 한 번 말한다. 저장하는 동안 입력은 `fieldset`으로, 선택 목록은 자기 `disabled`로(Radix는 `pointerdown`에 열리고 `fieldset`을 읽지 않는다), 막대의 버튼은 `aria-disabled`("저장 중…")로 막는다(`disabled`는 포커스를 떨어뜨린다). 읽기 전용이면 막대가 없고 `save`도 하지 않는다. 같은 저장 오류가 다시 나면 배너를 새로 그려 다시 알린다.
  - **되돌리기**: 초안과 입력한 키를 마지막으로 저장한 상태로 돌린다. 입력한 키가 있을 때만 확인을 받는다. 키체인에서 지우지 못한 키는 남는다(9.2). 막대의 버튼이 사라지면(저장 성공, 되돌리기) 포커스는 지금 탭 버튼으로 간다.
  - 저장 검사에 걸리면 그 필드가 있는 탭(과 그 연결의 행)을 연다. 저장 오류는 탭 위 배너이고 배너로 스크롤한다. 연결·웹훅 이름 문제는 추가 행 아래에 보인다. 떠나기 확인은 없다(9.3: 저장하지 않고 떠나면 버린다).
- **전사 탭** (ONB-01, ONB-02, ONB-07): 모델 묶음은 모델 선택(5.1의 세 모델, 개발용 `tiny`는 고르게 하지 않는다), 파일별 상태(설치됨 / 없음 / 받는 중 X% (받은/전체 MB), 이어받을 `.part`가 있으면 받아 둔 양)와 받는 동안의 진행 막대, 다운로드·직접 가져오기(빠진 파일이 있을 때, 상태를 읽지 못하면 직접 가져오기만), 받는 동안에는 취소와 진행 막대만, 모델 다운로드 주소(`model_base_url`)다. 처리 묶음은 전사 백엔드(자동 / GPU / CPU 분할 선택. 숨긴 네이티브 라디오라 화살표 키로 고른다. 행 레이블이 `aria-labelledby`로 이름 짓는다), 용어집(레이블 옆에 개수). 자동 백엔드에서 `gpu_failed`면 "GPU 전사에 실패해 CPU로 처리하고 있습니다"와 GPU로 골라 저장하면 지워진다는 안내를 보인다.
  - 모델과 주소는 다른 설정처럼 저장 버튼으로 저장한다. 다운로드·가져오기는 누르면 바로 돈다. 둘 다 `settings.json`의 모델과 주소를 쓰므로, 저장하지 않은 모델·주소 변경이 있으면 두 버튼을 막고 먼저 저장하라고 안내한다. 화면에 고른 값과 다른 옛 값으로 받는 일이 없게 하려는 것이다. 받는 동안에는 모델 선택도 막는다.
  - 진행률은 `model://download`로 받는다. 취소는 오류로 보이지 않는다. 받기·가져오기 오류는 공용 배너가 아니라 전사 탭 안에 보인다.
- **요약(LLM) 탭** (ONB-04, SUM-07, SUM-08): 연결은 행 목록이다. 행은 이름, 호스트, "로컬"/"클라우드" 꼬리표, 기본 연결이면 "기본"을 보이고(이름은 "회사 클라우드, 클라우드, api.example.com, 기본 LLM"처럼 이름부터), 누르면 그 자리에서 펼쳐진다(`aria-expanded`, 한 목록에 하나, 높이는 motion `layout`). 펼친 행에 Base URL, 모델, API 키, 컨텍스트 토큰, 응답 시간 제한, 로컬 여부, "연결 삭제". 마지막 행이 이름 입력과 "연결 추가"(Enter로도)이고, 추가한 연결은 펼쳐져 있다. 행을 지우면 포커스는 이름 입력으로 간다. Slack 탭의 웹훅도 같은 행 목록이다(행에 "키체인에 저장됨"/"URL 입력 안 됨", 펼치면 웹훅 URL, "테스트 메시지 보내기"(ONB-06, 7.1), "웹훅 삭제"). 클라우드 연결은 Base URL 아래에 "요약할 때 전사본 전문이 이 주소로 전송됩니다"를, 로컬 연결은 서버의 컨텍스트 길이를 컨텍스트 토큰 이상으로 맞추라는 안내(Ollama `OLLAMA_CONTEXT_LENGTH`, LM Studio Context Length, 9.3)를 보인다. 목록 아래 묶음에 기본 LLM 선택이 있고, 로컬 연결이 하나라도 있으면 "새 회의를 기본으로 로컬에서 요약"(`summarize_local_by_default`) 스위치를 두고 저장 버튼으로 함께 저장한다. 로컬 연결이 없으면 스위치를 감추고 `false`로 저장한다(보이지 않는 값이 켜진 채 남지 않게).
- **조사**: 화면 글자에 "(으)로"를 쓰지 않는다. `lib/utils.ts`의 `josa`가 이름의 마지막 글자로 고른다(받침 있음 → "으로", 받침 없음·ㄹ·한글 아님 → "로"). "{이름}({호스트})"는 괄호 속이 아니라 이름으로 고른다. 이 문서의 "{이름}(으)로"는 그 자리를 뜻한다. Rust 오류 문구의 "을(를)" 같은 표기는 그대로다.
- **모델 받기 상태**: 받기는 앱에 하나이고 `ipc.ts`의 모듈 변수에 둔다(`startModelDownload`, `modelDownload`, `modelDownloadFailure`). 화면을 떠나도 받기는 계속되고, 홈 설정 줄과 전사 탭은 열릴 때 같은 받기를 이어서 보여 준다. 받기가 끝나면(성공·실패·취소) `model_status`를 다시 읽는다. 마지막 진행률 이벤트는 해시 확인과 이름 바꾸기 전에 오므로 이벤트로 판단하지 않는다. 실패 이유는 다음 받기나 가져오기 성공 때까지 남아, 화면이 닫혀 있을 때 실패해도 다음에 열면 보인다.
  - 직접 가져오기는 `tauri-plugin-dialog`의 파일 열기로 고른 경로를 `import_model`에 넘긴다. 권한은 `dialog:allow-open` 하나만 준다(`src-tauri/capabilities/default.json`).

|---|---|
| `id` | 회의 id |

| `position` | 기다리는 동안 1부터 세는 대기 순서. 실행 중이면 `null` |

### 10.3 색상 토큰

색·글꼴·모양·모션 토큰과 대비 수치의 기준은 [디자인 시스템 2~5](design-system.md#2-타이포그래피)다(Paper & Pulse, 2026-10-15). 회사 서비스에서 이식했던 토큰(`mainBlue`, `cool700` 등)은 리디자인 0단계에서 새 토큰으로 바꾸고 지웠다. 여기에는 코드가 지킬 연결 규칙만 둔다.

`src/styles/theme.css`:

- **`@theme`**: 디자인 시스템 토큰을 같은 이름으로 둔다. 색(`bg-paper`, `text-ink-2`, `border-line-strong` …), 글자 크기(`text-display-m`, `text-body` …, 줄 높이·자간·굵기 포함. 글꼴은 `font-display`로 따로 고른다), 모서리 `rounded-control`(10px)·`rounded-float`(16px), 그림자 `shadow-float`, 본문 폭 `max-w-doc`·`max-w-home`·`max-w-wide`, CSS 전환 곡선 `ease-out`·`ease-in`(`lib/motion.ts`와 같은 값), 지금 일어나는 일을 알리는 키프레임(`animate-breathe`, `animate-bar`, `animate-dot`, `animate-shimmer`, 첫 화면의 `animate-ring`).
- **이름 충돌**: 디자인 시스템의 `accent`(#4950B0)는 Tailwind에서 `primary`(shadcn 컴포넌트) 또는 `brand`(우리 코드)다. Tailwind의 `accent`는 shadcn 뜻 그대로 hover 바탕(= `sunken`)이다. `accent-press`, `accent-tint`는 디자인 시스템 이름 그대로 쓴다.
- **shadcn 의미 변수** (`:root`): `background` → `paper`, `card`·`popover` → `surface`, `muted`·`secondary`·`accent` → `sunken`, `muted-foreground` → `ink-2`, `border` → `line`(장식용 구분선), `input` → `line-strong`(입력란·셀렉트·스위치 경계, WCAG 1.4.11), `primary`·`ring` → brand, `destructive` → `danger-line`. chart·sidebar 매핑은 쓰지 않아 뺀다.
- **`cn`**: shadcn의 `cn` 패키지는 테마에 새로 넣은 글자 크기를 모르면 `text-body`를 색으로 읽어, `cn("text-body", "text-ink")`에서 크기를 버린다. 그래서 `lib/utils.ts`가 테마의 글자 크기·모서리·그림자를 알려 준 `cn`을 만들고, 컴포넌트는 `"cn"`이 아니라 `@/lib/utils`에서 가져온다. `shadcn add`로 넣은 컴포넌트는 import를 고친다(`lib/utils.test.ts`가 잡는다).
- **라이트 모드만**: `.dark` 변수 블록을 두지 않고, `@custom-variant dark (&:where(.dark, .dark *));`를 정의한다. 앱은 `.dark` 클래스를 쓰지 않으므로 생성된 컴포넌트의 `dark:` 클래스는 절대 적용되지 않는다. Tailwind 기본 `dark` 변형은 OS 다크 모드를 따르므로, 이 정의가 없으면 OS 다크 모드에서 화면이 반쯤 바뀐다.
- **스캔 범위**: `@import "tailwindcss" source("../");`로 `src/`만 스캔한다. 그러지 않으면 `docs/`에 적힌 클래스명까지 CSS에 들어간다. 개발용 미리보기도 `@source not "../preview";`로 뺀다(미리보기 패널의 클래스는 개발 서버에서만 생긴다).
- **포커스 표시**: `:focus-visible`에 2px brand 윤곽선과 2px 간격을 전역으로 건다(WCAG 2.4.7). 조작 요소는 `outline-none`을 쓰지 않는다. 예외는 셋이고, 모두 `outline-hidden`이라 Windows 고대비 모드에서는 윤곽선이 남는다: 홈 목록 행은 행 전체를 감싸는 `after:` 링을, 셀렉트·메뉴 항목은 키보드로 옮길 때 안쪽 2px 링(`focus:inset-ring-2`)을 쓴다(hover 바탕만으로는 1.2:1이다). 회의 문서의 제목과 본문 입력란은 글 둘레 대신 2px 브랜드 선(제목 아래, 본문 왼쪽 여백)이 포커스를 알린다(`paper` 위 6.3:1). 설정의 분할 선택은 라디오를 숨기므로 같은 윤곽선을 라디오의 레이블에 그린다(`has-focus-visible:`). 조작이 아닌 포커스 자리(전사본 패널 제목, 화면 제목)는 `tabIndex=-1`에 `outline-hidden`이다.
- **가리지 않기** (WCAG 2.4.11): `html`의 `scroll-padding`(위 4rem, 아래 10rem)이 포커스 스크롤을 48px 머리와 아래 스택(막대 + 독, 148px까지) 밖으로 둔다. Chromium에서 확인했고 WebKit은 확인하지 못했다. 편집기 캐럿은 이 스크롤을 거치지 않아 10.1처럼 직접 옮긴다. 설정 내용은 저장 막대와 독이 함께 떠도 마지막 행이 가리지 않게 아래를 더 비운다.
- **글꼴**: Pretendard Variable(본문·UI), Instrument Serif(포인트 제목의 라틴·숫자, 400), Noto Serif KR Variable(제목의 한글)을 패키지 CSS로 불러와, Vite가 `unicode-range`로 나뉜 파일을 `dist/assets/`에 번들한다. 외부 폰트 주소는 없다(CSP `default-src 'self'`가 막는다). `font-display`는 `"Instrument Serif", "Noto Serif KR Variable", serif`다. Instrument Serif에는 굵기가 하나뿐이라 `html`에 `font-synthesis: none`을 걸어 가짜 굵게를 막는다(이탤릭은 쓰지 않고, 한글 제목만 450~500, 디자인 시스템 2). `html`은 `word-break: keep-all`과 `overflow-wrap: break-word`로 한글을 단어 사이에서만 줄바꿈한다. 세리프 두 폰트에는 `tnum`이 없어 타이머는 Pretendard의 `tabular-nums`로 쓴다.
- **종이 질감**과 아이콘: `body` 바탕에 SVG 노이즈(`data:` URL, CSP `img-src data:`)를 3%로 깔고, lucide 아이콘의 획 두께를 1.75로 맞춘다.
- **모션**: 토큰은 `lib/motion.ts`에만 둔다. 나가는 화면과 배너는 나가는 동안(약 208ms) 마운트된 채라 `inert`로 감싸 탭 순서·접근성 트리·클릭에서 뺀다(`App.tsx`의 `Present`). 회의 문서는 요약이 끝나도 화면을 옮기지 않고, 홈으로 가는 것도 지금 화면이 그 회의일 때만이다. 문서의 보내기 막대와 전사본 패널은 포털이라 `inert`가 닿지 않으므로 각자 `Present`로 감싸고, 화면이 나가기 시작하면(`useIsPresent`) 함께 나간다. `main.tsx`가 `<MotionConfig reducedMotion="user">`로 감싸고, 테스트는 `test-setup.ts`의 `MotionGlobalConfig.skipAnimations`로 애니메이션을 건너뛴다. CSS 키프레임은 `motion-safe:` 뒤에만 건다(shadcn 대화상자·셀렉트의 `animate-in`/`animate-out` 포함). 스위치 손잡이, 설정의 탭·분할 선택 표시, 행 펼침, 저장 막대는 motion이라 `MotionConfig`가 이동을 끈다.
- Radix는 위치 계산에 인라인 style을, motion의 `popLayout`은 `<style>` 요소를 쓴다. 둘 다 CSP의 `style-src 'unsafe-inline'`로 허용된다.

### 10.4 LLM 출력 표시 안전 규칙 (eng review D6)

LLM 요약과 전사본은 외부에서 온 텍스트다. 웹뷰는 `send_to_slack`, `set_secret` 같은 명령을 부를 수 있으므로, 이 텍스트가 HTML이나 스크립트로 실행되지 않게 두 겹으로 막는다.

1. **HTML을 그리지 않는다.** 제목과 요약은 `<textarea>` 일반 텍스트로 편집한다. 요약을 읽는 문서로 보일 때(10.1 문서 보기)는 Markdown 라이브러리를 쓰지 않고 우리 줄 파서(`parseDoc`)가 줄마다 모양을 알아본 뒤 React 요소와 글자 노드로만 그린다. 알아보는 것은 제목·목록·담당자·기한·"없음"·"미정"뿐이고, 굵게·링크·HTML 태그는 쓴 글자 그대로 보인다. `dangerouslySetInnerHTML`은 쓰지 않는다. 링크는 opener 플러그인으로만 연다.
2. **CSP를 켠다.** `src-tauri/tauri.conf.json`의 `app.security.csp`를 템플릿 기본값 `null`에서 아래로 바꾼다. 데스크톱 개발 모드(`tauri dev`)는 `devUrl`을 직접 불러와 CSP를 주입하지 않으므로, CSP 동작은 빌드된 앱에서 확인한다(`devCsp`는 데스크톱에서 효과가 없다).

```
default-src 'self'; script-src 'self'; connect-src ipc: http://ipc.localhost; img-src 'self' data:; style-src 'self' 'unsafe-inline'
```

- 단위 테스트: `<img src=x onerror=...>`가 든 요약이 텍스트로 표시되는지 확인한다.
- 릴리스 점검: 빌드된 설정에 CSP가 들어 있는지 확인한다.

## 11. 플랫폼별 설정

### 11.1 macOS

- **최소 버전**: `tauri.conf.json`의 `bundle.macOS.minimumSystemVersion`을 `"14.6"`으로 둔다.
- **`src-tauri/Info.plist`** (M2에서 추가. Tauri가 번들에 병합하고, `tauri dev`에서는 실행 파일에 내장한다):
  - `NSMicrophoneUsageDescription`: "회의를 녹음하기 위해 마이크를 사용합니다."
  - `NSAudioCaptureUsageDescription`: "화상 회의 상대방의 목소리를 녹음하기 위해 시스템 오디오를 사용합니다."
- **엔타이틀먼트** (`src-tauri/Entitlements.plist`, `bundle.macOS.entitlements`): `com.apple.security.device.audio-input`. 서명할 때 Hardened Runtime이 켜지므로(Tauri 기본값) 이것이 없으면 마이크가 막혀 0 버퍼가 된다.
- **개발 중 주의**: `tauri dev`에서는 권한 요청이 터미널 앱 이름으로 뜰 수 있다. 권한을 초기화하려면 `tccutil reset Microphone com.sije.meeting-summarizer`를 실행한다.
- **배포 서명** (사용자 결정 2026-10-16): Apple Developer 계정이 없어 ad-hoc 서명(`bundle.macOS.signingIdentity: "-"`)만 하고 공증은 하지 않는다. Hardened Runtime은 켜 두고 위 엔타이틀먼트를 넣는다(나중에 Developer ID로 공증할 때도 필요하다). 내려받은 앱은 처음 열 때 시스템 설정 > 개인정보 보호 및 보안의 "그래도 열기"를 한 번 거친다(`docs/install.md`). ad-hoc 서명은 빌드마다 cdhash가 바뀌어 TCC가 다른 앱으로 볼 수 있으므로, 업데이트할 때마다 마이크·시스템 오디오 권한을 다시 허용해야 할 수 있다. 실제 서명으로 바꾸려면 워크플로의 주석 처리된 `APPLE_*` 값을 저장소 Secrets로 채운다(`APPLE_SIGNING_IDENTITY`가 `"-"`보다 우선한다).
- **`libclang_rt.osx.a` 링크** (`src-tauri/build.rs`): `tauri build`는 배포 대상(deployment target)을 `minimumSystemVersion`인 14.6으로 정한다. 그러면 ggml-metal의 `@available` 검사가 `__isPlatformVersionAtLeast` 호출로 남는데, rustc는 이 함수가 든 clang 런타임을 링크하지 않아(`-nodefaultlibs`) 링크가 실패한다. 그래서 macOS 빌드는 `xcrun clang --print-resource-dir` 아래 `lib/darwin/libclang_rt.osx.a`를 링크한다. 그냥 `cargo build`는 지금 macOS 버전을 대상으로 해서 검사가 빠지므로 드러나지 않았다. Handy의 `build.rs`(MIT, 5197faf)와 같은 방법이다(13).
- **OS 알림** (APP-03): 플러그인(`notify-rust` → `mac-notification-sys`)은 `NSUserNotificationCenter`를 쓴다(macOS 14부터 지원 중단 표시가 붙었지만 동작한다). 알림마다 스레드 하나가 클릭이나 닫기를 기다리고, 클릭은 메인 런 루프의 대리자로 온다. `on_action`을 등록했으므로 모든 알림이 그렇다. 배너를 눌러도, 알림 센터에 남은 것을 나중에 눌러도 그 회의로 간다. 앱이 꺼졌다 켜진 뒤에는 이전 알림을 눌러도 회의로 가지 않는다(기다리던 스레드가 없다). `tauri dev`에서는 알림이 터미널 앱 이름으로 뜨고 클릭이 터미널을 연다. 배포 번들에서는 번들 식별자 `com.sije.meeting-summarizer`로 뜬다. OS 알림 설정과 개인정보 보호 및 보안의 앱 이름은 번들 이름(`productName` = `meeting-summarizer`)이다. M6에서 이 이름을 그대로 두기로 했고(2026-10-16), 그 목록을 가리키는 안내 문구(일반 탭의 알림 안내, 시스템 오디오 테스트의 권한 안내)는 `'meeting-summarizer'`라고 쓴다. 헤더·트레이·알림 제목은 "회의 요약"이다.
  - **기다리는 스레드의 비용**: 메인 스레드가 아닌 곳에서 기다리는 알림마다 mac-notification-sys는 메인 런 루프에 0.5초마다 도는 `NSTimer`를 걸어 `deliveredNotifications`를 훑는다. 스레드와 타이머는 알림이 알림 센터에서 사라질 때(클릭, 닫기, 알림 센터에서 지우기)에야 끝난다. 그래서 몇 주씩 켜 두는 트레이 앱에서는 읽지 않은 알림만큼 쌓인다.
  - 지우면 끝난다: 알림이 `deliveredNotifications`에서 빠지면 다음 타이머가 자동 닫힘으로 처리해 스레드가 돌아온다. 플러그인 2.7.0의 `remove_active`·`remove_all_active`는 macOS·Windows에서 아무것도 하지 않고 mac-notification-sys에도 지우는 API가 없어, objc2-foundation(이미 쓰는 크레이트에 `NSUserNotification`·`NSBundle` 기능만 더했다)으로 직접 지운다.
  - **포커스 때 지우기**: 메인 창이 포커스를 얻으면(`WindowEvent::Focused(true)`, 메인 스레드에서 온다) `NSUserNotificationCenter::removeAllDeliveredNotifications`를 부른다. 녹음자가 앱을 보고 있으므로 남은 알림은 이미 지난 것이다. 그래서 이 앱의 알림은 앱이 앞으로 올 때마다 알림 센터에서도 사라지고, 0.5초 안에 기다리던 스레드와 타이머가 모두 끝난다. 쌓이는 것은 창을 보지 않는 동안 온 알림뿐이다. 알림을 눌러 앱이 열려도 같다(누른 알림은 그 자리에서 끝나고, 창이 앞으로 오며 나머지가 지워진다). 상한은 두지 않는다: 몇 개 뒤에 완료 알림이 조용히 끊기는 편이 더 나쁘다.
  - 번들 식별자가 없는 프로세스(그냥 실행한 바이너리, 테스트)에서는 `defaultUserNotificationCenter`가 nil이고, objc2의 바인딩은 그때 패닉한다(릴리스는 `panic = "abort"`라 앱이 꺼진다). 그래서 `NSBundle::mainBundle().bundleIdentifier()`가 있을 때만 부른다. 알림 센터가 쓰는 것도 이 식별자다(mac-notification-sys가 `tauri dev`에서 터미널의 것으로 바꿔 끼운다. 그래서 개발 중에는 터미널 이름으로 온 알림도 함께 지워질 수 있다).

### 11.2 Windows

- **설치 파일**: NSIS, `installMode: "currentUser"`, 설치 화면은 한국어(`src-tauri/tauri.windows.conf.json`). 관리자 권한 없이 사용자 단위로 설치한다(NFR-06). 파일럿 동안 새 버전은 같은 설치 파일로 덮어 설치한다. MSI는 쓰지 않는다.
- **WebView2**: Tauri 기본값(`downloadBootstrapper`)을 그대로 쓴다. Windows 10/11 대부분에는 WebView2가 이미 설치돼 있다. 없는 PC에서는 WebView2 설치에 관리자 권한을 요구할 수 있다(NFR-06의 예외).
- **Vulkan 로더**: `vulkan-1.dll`을 `$INSTDIR`(실행 파일 옆)에 설치한다(5.4).
- **CPU**: AVX2가 없는 CPU는 전사가 4~10배 느리다(Meetily #306). 첫 실행 때 감지해서 "이 PC는 처리가 오래 걸릴 수 있습니다"를 안내한다.
- **OS 알림** (APP-03): 토스트(`tauri-winrt-notification`)의 클릭은 토스트가 화면에 있는 동안만 앱으로 온다. 알림 센터로 넘어간 뒤 누르면 OS가 앱을 실행하고, 단일 실행(APP-06)이 메인 창만 앞으로 가져온다(회의로 가지 않는다). 토스트의 앱 ID(AUMID)는 설치된 앱에서만 번들 식별자이고, `target\debug`·`target\release`에서 실행하면 PowerShell의 것을 쓴다. 실제 토스트 클릭은 아직 Windows에서 확인하지 않았다(로드맵 M5). 기다리는 스레드는 토스트가 화면에서 사라질 때(`Dismissed`, 시간 초과 포함) 끝나 쌓이지 않으므로, 11.1의 포커스 때 지우기는 Windows에서 하지 않는다.

### 11.3 배포 빌드

- **워크플로** (`.github/workflows/build.yml`): 수동 실행(workflow_dispatch)이나 `v*` 태그 push에서 macOS Apple Silicon(`aarch64-apple-darwin`, `.dmg`)과 Windows x64(NSIS `-setup.exe`)를 만든다. GitHub 릴리스는 만들지 않고 workflow artifact로 올리며, artifact는 30일 뒤 지워진다. 액션은 모두 커밋 SHA로 고정했다. 태그 실행이면 태그(`v` 제외)가 `tauri.conf.json`의 `version`과 같은지 먼저 확인한다.
- **번들 대상**: macOS `app`·`dmg`(`tauri.conf.json`), Windows `nsis`(`tauri.windows.conf.json`, Tauri가 Windows에서 병합한다).
- **배포**: 관리자가 artifact를 OneDrive에 올리고 동료에게 링크를 보낸다. 설치·업데이트·삭제 안내는 `docs/install.md`다. 자동 업데이트는 없다(eng review D2).
- macOS 빌드는 로컬 `tauri build`로 확인했다(11.1의 ad-hoc 서명). 워크플로는 아직 실행하지 않았고, Windows 빌드는 첫 Actions 실행에서 처음 확인한다.

### 12.3 요약 프롬프트 평가 (eng review D11)

- 고정 전사본 3개를 `src-tauri/tests/fixtures/`에 둔다(`{이름}.txt`, 한 줄에 발화 하나, + `{이름}.expected.json`). M0 녹음에서 만들고, 사람 이름·회사 정보는 익명화한다. 아직 사람이 넣어야 한다. 지금은 eval 경로를 확인하는 합성 전사본 `synthetic-weekly` 하나뿐이다(담당자 없는 할 일, 용어집 단어, 기각된 제안, "~하지 않기로", 뒤집힌 결정이 들어 있다). 형식은 그 폴더의 `README.md`.
  - 담당자가 언급되지 않은 액션 아이템이 있는 회의
  - 용어집 단어가 나오는 회의
  - 약 1시간 길이의 회의(구간 요약 경로 확인)
- `cargo test -- --ignored summary_eval`로 실행한다. 실제 LLM을 호출하므로 평소 테스트에서는 빠진다. 연결은 환경 변수로 준다: `SUMMARY_EVAL_BASE_URL`, `SUMMARY_EVAL_MODEL`, 선택으로 `SUMMARY_EVAL_API_KEY`, `SUMMARY_EVAL_CONTEXT_TOKENS`(기본 128,000), `SUMMARY_EVAL_LOCAL=1`. 환경 변수나 전사본이 없으면 통과하지 않고 무엇을 넣으라는 메시지로 실패한다. 전사본마다 실패를 모두 모아 한 번에 보고하고, 만든 요약을 출력한다.
- 형식 검사: 다섯 섹션이 모두 있음, 제목 20자 이하, 액션 아이템의 담당자(`[…]`)는 "미정"이거나 전사본·용어집에 있는 이름.
- **내용 검사** (eng review D17): 전사본마다 `expected.json`을 손으로 만든다.
  - 꼭 들어가야 할 결정과 할 일(`must`): 섹션별 키워드 묶음으로 적고, 묶음의 키워드가 모두 그 섹션에 나와야 한다.
  - 들어가면 안 되는 것(`must_not_in_decisions`): 기각된 제안 하나와 부정문("~하지 않기로") 하나 이상. "결정사항"의 한 줄에 묶음의 키워드가 모두 나오면 실패다.
  - 회의 중에 뒤집힌 결정 하나: 최종 상태는 `must`에, 뒤집히기 전 내용은 `must_not_in_decisions`에 적는다.
  - 담당자가 언급되지 않은 할 일(`unassigned`): 그 키워드가 모두 든 액션 아이템이 있어야 하고 담당자가 "미정"이어야 한다.
  - `expected.json`에 모르는 키가 있으면 읽을 때 실패한다(오타로 검사가 빠지지 않게).
  - 1시간 전사본에는 구간 경계에 걸친 결정을 하나 넣어 구간 요약과 재귀 축약(6.3)을 검사한다.
  - 키워드 검사라 표현이 크게 바뀌면 거짓 실패가 날 수 있다. 실패하면 사람이 출력을 읽고 키워드와 요약 중 어느 쪽을 고칠지 판단한다.
- 실행 시점: M4 끝, 그리고 프롬프트나 LLM 모델을 바꿀 때마다. 실행마다 API 비용이 몇 센트 든다.
