## Problem Statement

사내 회의 대부분이 기록되지 않는다. 그래서 불참자와 나중에 합류한 사람은 회의 내용을 다른 사람에게 다시 물어야 한다. Clova Note나 Zoom AI 같은 클라우드 도구는 비용 때문에 도입하지 않았다.

만들 것: 회의를 녹음하고, 로컬 Whisper로 전사하고, LLM으로 요약해 Slack으로 보내는 Windows/macOS 데스크톱 앱(Tauri 2).

## Demand Evidence

- 사용자 답변: "Clova Note, Zoom은 너무 비싸. 그리고 로컬 Whisper 모델정도면 충분히 전사가 가능하다고 판단했어. 그리고 요약기능도 넣을 예정이야."
- 정량 근거(인원 수, 월 회의 시간, 견적 금액)는 아직 없다. 수요는 **가설 단계**다.
- "로컬 Whisper면 충분하다"는 판단은 실제 사내 회의 녹음으로 확인된 적이 없다. The Assignment와 스파이크 S2에서 검증한다.

## Status Quo

- 사용자 답변: "대부분 기록 안 함." 따라서 경쟁자는 Clova Note가 아니라 **아무것도 안 하는 것**이다.
- 경고: 유료 도구 값을 낼 만큼 아프지 않다는 신호다.
- 기회: 기준선이 "없음"이라 녹음 → 전사 → 요약 → 공유만 돼도 순수한 이득이다. 화자 구분이나 편집 기능 없이도 가치가 있다.

## Target User & Narrowest Wedge

- **읽는 사람**: 회의 불참자, 나중에 합류한 사람 (사용자 답변: "회의 불참자/후입").
- **녹음하는 사람**: 회의 참석자 중 한 명. 읽는 사람과 **다른 사람**이다.
- 이 구조에서 나오는 결론 세 가지:
  1. 요약 품질이 곧 제품 품질이다. 불참자는 전사본이 아니라 요약을 읽는다.
  2. 공유 경로가 필수다. 불참자는 앱을 열지 않는다.
  3. 녹음자는 남을 위해 버튼을 누르는 셈이라, 녹음자의 수고가 최소여야 한다.
- **가장 좁은 쐐기**: 녹음 시작 → 종료 → (자동 전사·요약) → 검토 → Slack 전송. 사용자가 누르는 버튼은 3번(시작, 종료, 전송).
- 특정 인물은 아직 지명되지 않았다. Assignment에서 실제 불참자 한 명으로 검증한다.

## Constraints

- 지원 OS: macOS 14.6+ (Apple Silicon 우선), Windows 10/11 x64.
- 사내 PC가 섞여 있다. 설계 기준은 **GPU 없는 Windows 노트북**이다(기준 기기 사양은 Success Criteria 참고).
- 회의 환경: "대부분의 상황에서 조용한 회의실에서 회의" (대면 위주, 화상 회의도 지원).
- 녹음 입력: 마이크 + 시스템 오디오를 **첫 버전부터 함께** 지원한다. 마이크 먼저 내는 단계적 출시안은 사용자가 기각했다.
- 요약: 클라우드 LLM API가 기본이고, 로컬 LLM은 옵션이다.
- 공유: Slack Incoming Webhook.
- 소스 저장소 `sijecorp/meeting-summarizer`는 **비공개**다.
- 출발점: 기존 템플릿 (Tauri 2, React 19, TypeScript 6, Vite 8, bun, Rust edition 2024).
- UI 색상: 회사 서비스 색상 토큰(사용자 제공 Tailwind 설정)을 따른다.

## Premises

사용자가 8개 모두 동의했다.

1. 진짜 경쟁자는 "기록 안 함"이다. 성공 지표는 전사 정확도가 아니라 **실제로 녹음되는 회의 비율**이다. 설치 후 첫 녹음까지의 마찰을 최소화하고, 녹음 시작 → 종료 → Slack 전송을 클릭 3번 안에 끝낸다.
   - Codex는 "녹음 비율은 퍼널 지표이고, 진짜 결과는 불참자가 결정을 정확히 되찾는가"라며 이의를 제기했다.
   - 사용자는 이렇게 답하며 전제를 유지했다: "대부분의 상황에서 조용한 회의실에서 회의를 하는것이기 때문에 오디오 품질에 큰 무리는 없을거야. 기존 전제 유지하자"
   - 이 근거는 오디오 품질에 관한 것이라, 지표에 대한 반론에는 직접 답하지 않는다. 그래서 주 지표는 녹음 비율로 두고, 요약 품질은 **추가 작업 없이 자동으로 모이는 보조 지표**로만 기록한다(Success Criteria 참고).
2. 실시간 자막은 범위 밖이다. 녹음이 끝난 뒤 처리한다.
   - 목표: 1시간 회의 기준 Apple Silicon Mac 10분 이내, Windows(Vulkan) 25분 이내에 요약 완료.
3. 기본 모델은 원본 1.6GB가 아니라 `large-v3-turbo` q8_0(874MB)이다.
   - 언어는 `ko` 고정 + Silero VAD + 환각 문구 필터를 적용한다.
   - 원본 f16은 설정에서 고를 수 있다.
4. 지원 OS는 macOS 14.6+ (Apple Silicon 우선), Windows 10/11 x64다. Windows는 Vulkan 빌드를 기본으로 하고 CPU로 폴백한다.
5. macOS 배포에는 Apple Developer Program(연 $99) 서명·공증이 필요하다.
6. 비공개 저장소는 소스 전용이다. 설치 파일과 업데이터용 `latest.json`은 공개 releases 전용 저장소에 올린다.
   - 후속 결정(eng review D2, 2026-10-14): 자동 업데이트를 파일럿 뒤로 미뤘다. 파일럿 동안은 설치 파일을 사내 채널로 공유하고, 공개 releases 저장소는 파일럿 이후에 필요하다.
7. Slack 전송은 "자동 생성 → 녹음자가 검토·수정 → 전송 버튼" 순서다.
   - 앱은 확인 없이 채널에 올리지 않는다.
   - 웹훅 URL과 API 키는 OS 키체인에 저장한다.
8. Meetily(MIT)는 참고·차용 대상이다. 포크하지 않는다(대안 B 기각).

## Cross-Model Perspective

Codex(gpt-6.1-sol)가 이 대화를 보지 않은 상태에서 요약본만 읽고 검토했다.

- **가장 강한 버전**: "회의 인수인계" 도구. 한 사람이 녹음하고 한국어 요약을 검토한 뒤, 불참한 동료에게 결정사항·담당자·기한·미해결 질문을 Slack으로 보낸다.
- **가장 많은 걸 드러낸 답**: "회의 불참자/후입". 수혜자와 조작자가 다르므로, 녹음자의 수고를 거의 없애는 것이 채택의 관건이다.
- **틀렸다고 본 전제**: 전제 1. 녹음 비율은 퍼널 지표이고, 진짜 결과는 "불참자가 결정을 정확히 되찾고 행동할 수 있느냐"라고 봤다.
  - 처리 결과: 사용자는 오디오 품질을 근거로 전제를 유지했다. 이 근거는 지표 반론에 직접 답하지 않는다(Premises 1 참고).
  - 설계 반영: 검토 단계(전제 7), 담당자·기한을 추정하지 않는 요약 규칙, 자동 수집되는 요약 수정률 보조 지표.
- **48시간 프로토타입 제안**: 버려도 되는 Meetily 포크에 한국어 기본값, 검토 화면, Slack 전송만 추가하라. 2트랙 텍스트 중복 제거는 건너뛰라고 했다. "현장 vs 원격"은 화자가 아니라 오디오 출처라는 이유다.
  - 처리 결과: 포크 대신 슬림 빌드(대안 A)를 골랐다. 에코는 v1에서 게이팅으로 대응하고, 텍스트 중복 제거는 S4 결과에 따른 조건부 항목으로 남겼다.

## Approaches Considered

### Approach A: 슬림 빌드 (선택)

기존 템플릿 위에 직접 구현하고, Meetily와 Handy(둘 다 MIT)의 코드 일부를 차용한다. 작업량은 M (human: ~3-4주 / CC: ~2-3일)이다. 상세는 Recommended Approach에 있다.

### Approach B: Meetily 포크 (기각)

가장 빨리 동작하지만 기각했다. 이유는 세 가지다.
- 프론트엔드가 Next.js로 바뀌어 지금 템플릿을 버려야 한다.
- 실시간 믹싱 구조라 전제 2(녹음 후 처리)와 맞지 않는다.
- 쓰지 않는 코드(Parakeet, llama-helper 등)와 upstream과의 분기를 계속 떠안는다.

### Approach C: 녹음 중 청크 전사 (기각)

전제 2를 뒤집는 데다, 화상 회의 중 CPU를 같이 써서 통화 품질이 떨어질 위험이 있다. 대면 회의가 대부분인 지금 상황에서는 과투자다.

## Recommended Approach

**Approach A: 슬림 빌드.** 녹음이 끝난 뒤 처리하므로 Meetily의 실시간 믹서는 필요 없다. 에코를 줄이는 게이팅도 녹음이 끝난 뒤 합산 단계에서 한다. 다만 장치 변경과 절전 같은 **캡처 시점의 문제는 그대로 남는다**(아래 녹음 단계에서 다룬다).

`cpal` 0.18은 문서상 macOS 14.6+와 Windows 양쪽에서 시스템 오디오 루프백을 지원한다. 이것이 사실이면 OS별 네이티브 캡처 코드가 필요 없다. 단, 아직 검증되지 않았으므로 코드 작성 전에 **스파이크 S1**으로 확인한다. 실패하면 OS별 네이티브 캡처로 바꾼다.

### 처리 파이프라인

1. **녹음**
   - `cpal` 0.18로 두 입력을 동시에 연다: 기본 입력 장치(마이크)와 기본 출력 장치의 루프백(시스템 오디오).
   - **기록 형식**: 오디오 콜백은 샘플을 채널로 넘기기만 한다. 별도 기록 스레드가 모노 다운믹스 → 16kHz 리샘플 → 16-bit PCM WAV로 기록한다.
     - 용량: 트랙당 시간당 약 115MB, 두 트랙 합쳐 약 230MB.
     - 16kHz는 Whisper 입력 형식이라 녹음 후 별도 리샘플이 필요 없다.
   - **크래시 대비**: 기록 스레드가 5초마다 WAV 헤더의 길이 필드를 갱신한다. 강제 종료돼도 파일이 유효하고, 손실은 최대 5초다.
   - **시간축 정렬**: 두 장치와 무관한 단조 시계(녹음 시작부터의 경과 시간, 절전 구간 제외)를 기준으로 쓴다.
     - 어느 트랙이든 이 시계보다 뒤처지면 그 트랙에 무음을 채운다(양방향 규칙). Windows 루프백이 무음 구간에 데이터를 보내지 않는 경우와 마이크가 끊긴 구간이 모두 이 규칙으로 처리된다.
     - 장치 클럭이 빨라 트랙이 시계보다 앞서면, 10초마다 확인해 앞선 만큼 샘플을 버린다.
     - 허용 오차: 4시간 녹음 내내 두 트랙의 시간 차이 0.5초 이하.
     - 절전 구간은 시계에서 빠지므로 어느 트랙에도 무음이 들어가지 않는다.
   - **최대 길이**: 4시간. 3시간 50분에 경고하고, 4시간이 되면 자동으로 종료하고 처리 대기열에 넣는다.
   - **장시간 무음**: 두 트랙이 모두 15분 연속 무음이면 "녹음을 계속할까요?" 알림을 띄운다. 종료를 잊은 녹음 대비다.
   - **절전**: 녹음 중에는 시스템 절전을 막는다(`keepawake`). 덮개를 닫는 등으로 그래도 절전되면 길이에 따라 처리한다.
     - 5분 이하: 깨어난 뒤 이어서 녹음하고 중단 구간을 `meta.json`에 기록한다.
     - 5분 초과: 이어서 녹음하지 않는다. 절전 시점에서 녹음을 끝내 처리 대기열에 넣고, 깨어날 때 "절전으로 녹음이 종료되어 처리 중입니다" 알림을 띄운다. 회의실에서 덮개를 닫고 자리로 돌아간 뒤의 대화가 같은 회의에 붙지 않게 하려는 것이다.
   - **장치 변경·분리**
     - 스트림 오류(장치 분리 등)가 나면 2초 안에 새 기본 장치로 다시 연결한다.
     - 기본 장치 변경 감지: 1초마다 OS의 기본 입력·출력 장치 ID를 확인한다. 장치를 고정하지 않았는데 기본 장치가 바뀌면(예: 녹음 중 헤드셋 연결) 스트림 오류가 없어도 새 기본 장치로 다시 연결한다. 루프백이 이전 스피커를 계속 붙잡아 원격 발화를 잃는 일을 막는다.
     - 전환 중 끊긴 구간은 단조 시계 규칙으로 무음 처리하고, 화면에 경고 배너를 띄운다.
     - 설정에서 장치를 고정했는데 그 장치가 사라지면, 기본 장치로 바꾸고 경고한다.
   - **권한 감지**
     - 마이크: 실제 마이크는 바닥 잡음이 있어 완전한 0이 드물다. 그래서 녹음 시작 3초가 완전한 0이면 권한 경고 배너를 띄운다(닫을 수 있음).
     - 시스템 오디오: 녹음 중에는 경고하지 않는다. 대면 회의에서는 원래 무음이라 오탐이 나기 때문이다. 대신 첫 실행 온보딩과 설정 화면의 "시스템 오디오 테스트"가 테스트음을 재생하고 루프백에 소리가 잡히는지 확인한다.
   - **화상 회의 에코**: 합산할 때 **게이팅**을 적용한다(사용자 결정).
     - 시스템 오디오에 소리가 있는 동안 마이크 트랙을 낮춰(예: -20dB), 스피커에서 마이크로 다시 들어간 원격 발화를 줄인다.
     - 대가: 원격 참석자와 동시에 말한 현장 발화는 작게 녹음된다.
     - 헤드폰 사용은 권장으로만 안내한다.
     - 효과는 **스파이크 S4**로 확인한다.
2. **전처리**: 녹음이 끝나면 두 트랙을 게이팅을 적용해, 클리핑이 나지 않게 합산한 한 트랙으로 만든다.
3. **전사**
   - **구간 처리**: VAD로 찾은 무음 지점에서 약 10분 단위로 자른다. 구간을 순서대로 전사하고, 끝날 때마다 `transcript.partial.jsonl`에 추가한다. 이 구간이 일시정지·재개 단위다.
   - **실행 파라미터**: `whisper-rs`, `language=ko`, Silero VAD, `no_context`, `suppress_nst`.
   - **백엔드 선택**: 설정은 자동 / GPU / CPU 세 가지다. 자동일 때 규칙은 다음과 같다.
     - macOS는 Metal을 쓴다.
     - Windows는 Vulkan을 쓴다. Vulkan 장치가 없거나 초기화에 실패하면 CPU로 바꾼다.
     - Vulkan 런타임이 없는 PC에서도 앱이 실행되도록 Vulkan 로더(`vulkan-1.dll`)를 앱과 함께 배포한다(Meetily #685).
   - **처리 중 크래시** (후속 결정 eng review D5, 2026-10-14: 전사는 자식 프로세스에서 돌리고, 워커 종료 코드로 크래시를 즉시 감지한다. 아래의 재시작 기반 판정은 [아키텍처 5.3~5.4](../architecture.md)로 대체됐다)
     - 정상 종료(트레이 "종료", OS 종료 신호)일 때는 진행 중인 회의를 `paused`로 기록한다. 그래서 다음 실행 때 `transcribing` + `backend=gpu` 상태가 남아 있다면 비정상 종료라는 뜻이다.
     - 비정상 종료를 감지하면 바로 GPU 실패로 단정하지 않는다. 같은 구간을 GPU로 한 번 다시 시도하고, 그 구간에서 또 비정상 종료가 나야 이 PC에 "GPU 실패"를 기록한다. OS 업데이트나 배터리 방전 한 번으로 GPU가 꺼지는 일을 막는다.
     - "GPU 실패"를 기록하면 이후 자동 모드는 CPU를 쓰고, 녹음자에게 "GPU 처리가 불안정해 CPU로 전환했습니다. 처리 시간이 길어집니다" 알림을 띄운다.
     - 설정에서 GPU를 강제로 다시 켤 수 있다.
     - 해당 회의는 마지막으로 끝난 구간부터 다시 처리한다.
   - **CPU 폴백 모델**: CPU로 돌 때의 기본 모델(`large-v3-turbo` q8_0 또는 `medium` q5_0)은 스파이크 S2 결과로 정한다.
   - **용어집**(사람 이름, 제품명)
     - 주 경로: 요약 LLM 프롬프트에 넣어 표기를 바로잡는다.
     - Whisper initial prompt에도 넣을지는 S2에서 용어집 유무를 비교해 정한다. initial prompt는 약 224토큰에서 잘리므로, 넣는다면 앞쪽 항목만 들어간다.
   - **환각 필터**: 전사 결과에서 알려진 환각 문구(예: "시청해주셔서 감사합니다")를 제거한다.
4. **요약**
   - **클라이언트**: OpenAI 호환 Chat Completions 클라이언트 **하나**(`base_url`, `api_key`, `model`)로 클라우드 API와 로컬 Ollama/LM Studio를 모두 처리한다.
   - **형식**: 제목(자동 생성) / 결정사항 / 액션 아이템(담당자·기한) / 주요 논의 / 미해결 질문.
   - **추정 금지 규칙**: 발화에 명시되지 않은 담당자나 기한은 "미정"으로 쓰고 추정하지 않는다. 검토 화면에서 "미정" 항목을 강조한다.
   - **긴 회의**: 전사본이 설정된 컨텍스트 한도를 넘으면 구간별로 요약한 뒤 합친다.
   - **원본 보관**: LLM이 만든 원본 요약(`summary.generated.md`)을 따로 저장한다. 보조 지표 측정에 쓴다.
   - **실패 처리**: 네트워크 없음, 키 없음·만료, 할당량 초과, 로컬 LLM 미실행, 구간 일부 실패가 대상이다.
     - 전사본은 그대로 보존한다.
     - 검토 화면에 원인을 보여주고 "요약 다시 실행"을 제공한다. 이때 다른 LLM 설정을 고를 수 있다.
     - 요약 없이 Slack으로 보내지는 않는다. 전사본 복사·파일 저장은 할 수 있다.
   - **데이터 반출 고지와 회의별 선택**: 클라우드 LLM을 쓰면 전사본 전문이 공급자에게 전송된다. 그래서 고지와 선택은 **요약이 실행되기 전에** 이뤄진다.
     - 설정 화면, 녹음 중 화면, 처리 중 화면에 "요약은 {공급자}로 전송됩니다"를 표시한다.
     - 로컬 LLM이 설정돼 있으면 녹음 중 화면과 처리 중 화면에 "로컬로 요약" 토글을 둔다. 기본값은 설정값이라 클릭 수가 늘지 않는다. 요약이 시작되기 전까지(전사 진행 중 포함) 바꿀 수 있다.
     - 검토 화면에는 사실대로 "{공급자}로 전송됨"이라고 적는다.
5. **검토**: 녹음자가 제목과 요약을 수정한다. 원문 전사본도 함께 볼 수 있다.
6. **전송**
   - Slack Incoming Webhook의 `markdown` 블록으로 보낸다(Block Kit, 최대 12,000자). 웹훅이 이 블록을 받는지는 스파이크 S5로 확인한다.
   - **메시지 머리말**: 제목, 일시, 녹음 길이, 녹음자 이름(설정값).
   - **메시지 꼬리말**: 작은 글씨로 "AI 요약 · 녹음자 검토 완료 (수정 N곳)"를 붙인다. 읽는 사람에게는 사람이 검토했다는 신호가 되고, 파일럿 동안 채널에서 바로 보조 지표를 집계할 수 있다. 같은 값을 `meta.json`에도 기록한다.
   - **채널**: 웹훅은 이름을 붙여 여러 개 저장한다.
     - 웹훅이 1개면 자동으로 선택된다.
     - 여러 개면 마지막으로 보낸 채널이 기본 선택된다.
   - **전송 실패**: 요약은 남아 있고, 다시 보내거나 클립보드로 복사할 수 있다.
7. **저장**: 회의마다 앱 데이터 폴더 아래 `meetings/{id}/`를 하나 만든다.
   - 녹음 원본: `mic.wav`, `system.wav`
   - 전사: `transcript.partial.jsonl`(진행 중), `transcript.json`(완료)
   - 요약: `summary.generated.md`(LLM 원본), `summary.md`(검토·전송본)
   - 메타데이터: `meta.json`
   - DB는 쓰지 않는다.
   - **상태 흐름** (`meta.json`에 기록): `recording` → `recorded` → `transcribing` → `transcribed` → `summarizing` → `review` → `sent` 또는 `archived`(전송 안 함). 각 단계에는 실패 상태가 있고, 정상 종료로 멈춘 처리는 `paused`다.
   - **회의 정리**: 검토 화면에서 "전송 안 함"을 누르면 `archived`가 되어 미전송 목록에서 빠진다. 어느 상태에서든 회의를 삭제할 수 있다(폴더 전체 삭제).
   - **앱 시작 시 복구**
     - `recording` 상태로 남은 회의는 "중단된 녹음"으로 표시하고 "처리 계속 / 삭제"를 제안한다.
     - 처리 단계에서 멈춘 회의는 대기열에 다시 넣어, 마지막으로 끝난 구간부터 이어서 처리한다.
8. **모델**: 첫 실행 때 Hugging Face(`ggerganov/whisper.cpp`)에서 Whisper 모델과 Silero VAD 모델을 내려받는다. 진행률 표시, 이어받기, 해시 검증을 한다. 설치 파일에는 포함하지 않는다.

### 앱 동작 규칙

- **동시성**
  - 녹음은 한 번에 하나만 할 수 있다.
  - 처리는 선입선출(FIFO) 대기열이다.
  - 녹음이 시작되면 진행 중인 전사는 whisper 중단 콜백(abort callback)으로 **즉시** 멈춘다. 녹음이 끝나면 그 구간을 처음부터 다시 처리한다. 잃는 것은 최대 한 구간의 처리 시간이다. 화상 회의와 전사가 CPU를 두고 경쟁하지 않게 하려는 것이다.
  - 로컬 LLM 요약도 같은 규칙으로 즉시 중단하고, 녹음이 끝나면 다시 실행한다. 클라우드 LLM 요약은 PC 자원을 거의 쓰지 않으므로 계속 진행한다.
- **창 닫기**
  - 녹음이나 처리 중에 창을 닫으면 트레이로 내려가 계속 진행한다.
  - 트레이 메뉴의 "종료"는 진행 중인 작업이 있으면 확인을 받는다.
  - 완전히 종료한 경우 다음 실행 때 마지막으로 끝난 구간부터 재개한다.
- **완료 알림**
  - 처리가 끝나면 OS 알림을 보낸다.
  - 알림을 누르면 **그 알림의 회의** 검토 화면으로 간다.
  - 앱을 그냥 열면 홈(녹음 버튼 + 미전송 회의 강조)으로 간다. 그래서 바로 새 녹음을 시작할 수 있다.
  - 트레이 아이콘에 미전송 상태를 표시한다. `archived` 회의는 미전송으로 치지 않는다.
- **첫 설정 (온보딩)**: 모델 다운로드 → 마이크·시스템 오디오 권한과 테스트 → 연결 설정 → 테스트 전송.
  - 연결 설정은 녹음자가 직접 입력한다(API 키, 웹훅 URL). 비밀값은 입력 즉시 키체인에 저장한다.
  - 후속 결정(eng review D3, 2026-10-14): 설정 파일 가져오기는 평문 비밀값 파일을 만들지 않기 위해 v1에서 뺐다. 키와 URL의 전달 방법은 Open Question 3이다.

### R2-1 — feasibility (blocking)

**Problem**

> 시간축 정렬은 마이크 트랙을 기준 시계로 삼고 '시스템 트랙이 뒤처질 때'만 무음을 채운다. 그런데 장치 변경·분리 규칙은 마이크 스트림이 끊긴 경우에도 '끊긴 구간은 무음으로 채운다'고 한다. 기준 시계인 마이크가 끊기면 마이크 샘플 수가 멈추므로 끊긴 길이를 잴 기준이 없고, 그 사이 시스템 트랙은 계속 쌓여 마이크보다 앞서게 된다. 시스템 트랙이 앞서는 경우(마이크 끊김, 두 장치의 클럭 드리프트)의 규칙이 없어 재연결 이후 녹음 끝까지 두 트랙이 어긋난 채 합산되고, 화상 회의에서는 원격 발화와 현장 발화가 겹쳐 전사 품질이 떨어진다. S1 통과 기준(60분에 0.5초)도 최대 길이 4시간에서는 약 2초 어긋남을 허용한다.

**Remedy**

> 정렬 기준을 두 장치와 독립된 시계(예: 절전 구간을 뺀 단조 경과 시간)로 바꾸고, 어느 트랙이든 뒤처지면 그 트랙에 무음을 채우는 양방향 규칙으로 정한다. 마이크가 끊긴 구간의 길이도 이 시계로 잰다. 드리프트 허용치를 4시간 기준으로 다시 정하고, 넘으면 보정(샘플 삽입·삭제 또는 리샘플 비율 조정)할지 정한다.

### R2-2 — consistency (blocking)

**Problem**

> S4가 실패하면 '트랙별로 전사한 뒤 타임스탬프로 병합'으로 바꾼다고 한다. 그러나 스피커를 쓰면 마이크 트랙에도 원격 발화가 다시 녹음되므로, 트랙별로 전사해도 원격 발화가 두 트랙에서 각각 전사되고 병합하면 같은 문장이 두 번 들어간다. S4가 재는 실패 원인(중복 문장)을 이 대안은 없애지 못한다. 중복을 없애려면 텍스트 수준 중복 제거가 필요한데, 문서는 이를 v1 범위에서 뺐다(Cross-Model Perspective, Open Question 8).

**Remedy**

> S4 실패 시 실제로 중복을 없애는 경로를 하나 고른다. (a) 병합할 때 시스템 트랙 발화와 시간이 겹치고 텍스트가 비슷한 마이크 트랙 구간을 버리는 중복 제거를 v1에 조건부로 넣는다. (b) 시스템 트랙에 소리가 있는 동안 마이크 트랙을 낮추는 게이팅을 한다. (c) 스피커를 쓰는 화상 회의는 지원 범위에서 빼고 헤드폰을 필수로 안내한다. 고른 경로를 S4의 '실패 시' 칸, 녹음 단계의 화상 회의 에코 항목, Open Question 8에 맞춘다.

### R2-3 — consistency (blocking)

**Problem**

> 처리 중 크래시 판정은 '다음 실행 때 meta.json에 transcribing + backend=gpu가 남아 있으면 GPU 크래시'다. 그런데 창 닫기 규칙은 처리 중에도 트레이 '종료'로 완전히 종료할 수 있고 다음 실행 때 재개한다고 한다. 정상 종료, OS 재시작·업데이트, 배터리 방전도 같은 상태를 남기므로 GPU 실패로 잘못 기록되고, 이후 그 PC는 자동 모드에서 계속 CPU(목표 60분)를 쓴다. 녹음자는 왜 느려졌는지 알 수 없다.

**Remedy**

> 정상 종료 때는 상태를 일시정지(예: paused)로 기록해 크래시와 구분한다. 크래시로 보이는 경우에도 바로 GPU 실패로 기록하지 말고, 같은 구간을 GPU로 한 번 다시 시도해 또 크래시할 때만 기록하는 등 판정 기준을 정한다. GPU 실패로 바꿨을 때 녹음자에게 알리는지도 정한다.

### R2-4 — consistency (blocking)

**Problem**

> 녹음이 시작되면 진행 중인 전사를 '현재 구간이 끝나는 시점'에 일시정지한다. 구간은 약 10분 분량이라 CPU 폴백(1시간에 최대 60분)에서는 다음 화상 회의가 시작된 뒤 최대 약 10분, Vulkan에서도 수 분 동안 전사가 계속 자원을 쓴다. 이 규칙이 밝힌 목적('화상 회의와 전사가 CPU를 두고 경쟁하지 않게')과 맞지 않고, 대안 C를 기각한 위험이 그대로 생긴다. 녹음이 시작될 때 로컬 LLM 요약이 돌고 있는 경우의 규칙도 없다.

**Remedy**

> 녹음이 시작되면 whisper 중단 콜백(abort callback)으로 진행 중인 구간을 바로 멈추고, 재개할 때 그 구간을 처음부터 다시 처리한다(재개 단위가 이미 구간이므로 잃는 것은 최대 한 구간의 처리 시간이다). 로컬 LLM 요약에도 같은 규칙을 적용할지 정한다.

### R2-5 — completeness (blocking)

**Problem**

**Remedy**

> 일정 시간(예: 5분)을 넘게 절전됐다가 깨어나면 자동으로 이어 녹음하지 않는다. 절전 시점에서 녹음을 끝내 처리 대기열에 넣거나, '이어서 녹음 / 여기서 종료' 확인을 받는 것 중 하나를 정한다. 어느 쪽이든 깨어날 때 녹음 상태를 알림으로 알린다.

### R2-6 — completeness (blocking)

**Problem**

> 앱을 열면 가장 오래된 미전송 회의의 검토 화면으로 간다. 그런데 상태 흐름의 끝은 sent뿐이고, 보내지 않기로 한 회의를 닫거나 삭제하는 동작이 없다(삭제는 중단된 녹음에만 있다). 잘못 녹음했거나 공유하지 않을 회의가 하나라도 있으면 앱을 열 때마다 그 회의로 가고 트레이의 미전송 표시도 계속 켜진다. 새 녹음을 하려면 홈으로 돌아가는 클릭이 더 필요한데, 클릭 3번 기준은 '앱이나 알림을 여는 동작'만 제외한다. 회의 B의 완료 알림을 눌러도 더 오래된 회의 A로 간다.

**Remedy**

> '전송 안 함(보관)' 종료 상태와 회의 삭제를 추가하고 미전송 목록에서 뺀다. 알림을 누르면 그 알림의 회의로 가고, 앱을 그냥 열면 홈(미전송 강조 + 녹음 버튼)으로 가는 등 이동 규칙을 클릭 3번 기준과 맞게 정한다.

### R2-7 — completeness (blocking)

**Problem**

> 데이터 반출 고지는 설정 화면과 검토 화면에 표시하고, 로컬 LLM이 있으면 회의마다 '로컬로 요약'을 고를 수 있다고 한다. 그러나 요약은 전사가 끝나면 자동으로 실행되고 검토 화면은 그 뒤에 열리므로, 검토 화면에서 고지를 볼 때는 전사본이 이미 공급자에게 전송된 뒤다. 회의마다 고르는 시점(녹음 중, 종료 직후 등)이 정해지지 않아 민감한 회의에서 반출을 막을 수 없다.

**Remedy**

> 회의별 요약 경로를 고르는 시점을 요약 실행 전으로 정한다(예: 녹음 중 화면이나 종료 직후의 '로컬로 요약' 토글. 기본값은 설정값이라 클릭 수는 늘지 않는다). 검토 화면의 고지는 '전송됨'으로 사실대로 적는다.

### R2-8 — completeness (blocking)

**Problem**

> 요약 품질 보조 지표는 '자동 수집'이고 '녹음자에게 추가 작업이 생기지 않는다'고 한다. 그러나 앱에는 서버나 텔레메트리가 없고 summary.generated.md와 summary.md는 각 녹음자 PC의 앱 데이터 폴더에만 있다. 파일럿 팀의 수정률을 한곳에 모으는 경로가 없어 누군가 각 PC에서 파일을 받아야 하고, 이는 '자동 수집'과 '추가 작업 없음'에 맞지 않는다.

**Remedy**

> 수집 경로를 하나 정한다. 예: 수정률을 meta.json에 기록하고 Slack 메시지 끝에 작게 붙여 채널에서 바로 집계한다. 또는 설정의 '파일럿 지표 내보내기'로 파일럿 종료 때 한 번 모으고, 이 경우 '추가 작업 없음' 문구를 고친다.

### R2-9 — completeness (blocking)

**Problem**

> 장치 변경·분리 동작은 '스트림 오류가 나면' 새 기본 장치로 다시 연결한다. 그러나 블루투스·USB 헤드셋을 연결해 OS의 기본 출력 장치만 바뀌고 이전 장치는 남아 있으면 스트림 오류가 나지 않고, 루프백은 이전 장치(스피커)를 계속 붙잡아 이후 시스템 오디오가 비게 된다. 문서가 화상 회의에서 헤드폰을 쓰라고 안내하므로, 녹음을 시작한 뒤 헤드셋을 연결하는 흔한 경우에 원격 참석자 발화 전체를 잃는다. R1-12가 지적한 '이전 장치를 계속 붙잡는' 경우의 동작이 여전히 없다.

**Remedy**

> 기본 입력·출력 장치 변경을 감지하는 방법(OS 기본 장치 변경 알림 또는 주기적인 기본 장치 ID 확인)과 감지했을 때의 동작(장치를 고정하지 않았으면 새 기본 장치로 다시 연결, 끊긴 구간 처리, 경고)을 정한다. S1에 녹음 중 기본 출력 장치 변경 항목을 넣는다.
